# ADR · M6 后计划表与四条轨道（D-N1..N7）

- 状态：已定案 ｜ 决策人：lead ｜ 复核人：独立复核（文档门禁 + 设计评审，`.work` 论证不入库） ｜ 日期：2026-11-11 ｜ 基线：`0d8bbe0`
- 关联：第 17 章 **§17.9（本计划表权威落点）**、`docs/PROGRESS.md` §1/§4/§7；风险 `R-T8`（LLM 延迟/无流式）、
  `R-T12`（世界书字段子集/跑团模组仅设计）；范围外批次 H4/UC/WB2；编号 **029–060**。

## 1. 背景与红线

- M1–M6（001–028）、R2/R3、H4、UC、WB2 全部完成；收官审计结论：**第 17 章缺「M6 后计划表」**，
  导致场景编辑器/分享、条件 DSL 扩展、流式叙事（Q7-B）、Playwright/a11y（D-M6-11 复评）、发布形态
  （D-TEAM-3）、m3 叙事受控重基线、跑团世界模组 P0 等后续工作只能以 ADR 挂账、无法排期，也无法给
  进度文档分配编号。
- **红线（不放宽）**：唯一写入者 + CAS + `Idempotency-Key`；用户上传 JSON 永不执行（白名单谓词、
  无 eval/脚本）；API Key 不回显/不入库/不日志；旧 4 场景 golden 逐字不变；零新增运行时依赖；
  三步质量门（ruff/mypy/lint-imports/check_docs）+ web typecheck/build/dist 零漂移 + 浏览器 e2e。

## 2. 决策

### D-N1 编号与轨道（编号权威）

- 决策：把 M6 后工作收拢为四条轨道并分配单一全局编号区间——**N1 内容轨 029–036、N2 体验轨 037–044、
  N3 功能轨 045–048、N4 技术/发布轨 049–056、预留 057–060**。区间硬约束、篇数不足留空不后移、跨区间不借用；
  批次 ADR 编号 `D-N1-*`…`D-N4-*`；范围外小批沿用 `H4/UC/WB2` 风格（不占编号）。
- 理由：延续第 22 章「里程碑 → 全局唯一递增编号」机制，历史链接不失效；四轨道与用户优先级
  （内容→体验→功能→技术→文档）一一对应，便于按轨道整体推进。
- 被否选项：① 每个批次独立字母编号（`P1/P2…`）——会与既有 P0/P1 验收优先级、R2/H4 批次名混淆；
  ② 只写主题不写编号——无法满足第 22 章进度文档命名校验，等于继续挂账。
- 影响面：`docs/开发文档/第17章`（§17.9）、`docs/PROGRESS.md` §1/§4、`docs/开发文档/第22章` §22.3 注记、
  后续所有进度文档与 ADR 编号。
- 回写落点：第 17 章 §17.9.1/§17.9.2、PROGRESS §4、第 22 章 §22.3。
- 验收断言：`scripts/check_docs.py` PASS（头部下一编号 = §4 行内编号 = 029）；`docs/开发文档.md` 重建后一致。

### D-N2 优先级与出口门禁

- 决策：沿用用户指定顺序 **内容 → 体验 → 功能 → 技术 → 文档** 作为轨道优先级；每批出口必须同时满足
  §17.9.3 七项门禁（基线/四门/web/e2e/文档同批/契约同步/硬不变量）。**允许偏离**：用户明确要求先发布时，
  N4 的 049–053 可插队，仅在 PROGRESS §7 记录原因，不改变轨道边界。
- 理由：此前每个批次都因「先有可玩内容再谈技术」而避免空转；但发布就绪不依赖内容轨，提前做不阻塞内容。
- 被否选项：强制串行（内容轨全部完成才允许技术轨）——与「先给可下载版本」的用户诉求冲突，且发布项风险最低。
- 影响面：PROGRESS §7 下一步/启动顺序；第 17 章 §17.9.4。
- 回写落点：第 17 章 §17.9.3/§17.9.4。
- 验收断言：每批进度文档第 3 节列出七项门禁实测数字；缺失任一项即不允许标「已完成」。

### D-N3 发布就绪定义（N4 049–053）

- 决策：首个**可发布快照**定为 `0.2.0`（语义：0.1.0 为骨架，0.2.0 = M1–M6 + 用户内容批次可玩版本）。
  发布就绪 = ① 版本记录（`pyproject`/CHANGELOG/README 发布段与日期）；② 英文 README 与中文对齐；
  ③ 分发形态结论：**默认单机 zip/wheel + `play` 脚本**，Docker 给出评估结论与可选 `Dockerfile`（不承诺
  Compose/镜像仓库）；④ `uv build` wheel 干净 venv 安装冒烟 + `play -Check`；⑤ 发布 checklist 演练一次
  （CI/四门/e2e/demo/console/许可证/SECURITY/tag/release notes）。
- 理由：D-TEAM-3 已定「先版本记录/CHANGELOG 后评估 PyPI，Docker 等 `web/dist` 与 `web-build` CI 就绪后再做」；
  这些前置已全部就绪（tracked dist + CI web-build），现在可以收口。
- 被否选项：① 直接发 PyPI——包名/README/许可证元数据虽已备，但需要用户明确授权与更完整的 wheel 冒烟，
  本轮只做**可发布快照**，PyPI 留待用户拍板；② 只发 Docker 镜像——单机 SQLite + 静态 SPA 用 zip/wheel 更简单，
  镜像作为可选补充。
- 影响面：`pyproject.toml` 版本、CHANGELOG、README/README.en.md、SECURITY/发布段、第 17/19 章。
- 回写落点：第 17 章 §17.9.2 N4 行、README 发布段、CHANGELOG、PROGRESS §7。
- 验收断言：干净 venv `pip install dist/*.whl` 后 `python -m textgame.console --check` exit 0；
  `scripts/play.ps1 -Check` PASS；`git tag -a v0.2.0` dry-run 流程文档化（是否 tag/push 由用户拍板）。

### D-N4 流式叙事阶段 1 边界（N2 037–040）

- 决策：阶段 1 = **独立流式端点 + NDJSON 协议 + 前端 `fetch` `ReadableStream`**，默认关闭、默认路径
  仍走同步 `POST /turns`（`TurnResult` 契约不变）。约束：不新增 `EventType`；事件只在回合完整结束后提交
  （唯一写入者/CAS 不变）；前端禁用 `EventSource`（`security-scan.test.ts` 已 forbid，统一 fetch 流式便于
  带 `Idempotency-Key`/`AbortSignal`）；失败/超时降级为同步重试提示（手动）；离线模板路径单 chunk 返回。
  若 037 评估结论为「暂不做」（如 litellm 流式不可控/收益不足），只交评估文档并关闭 038–040。
- 理由：R-T8 真实 LLM 首回合 7–8s、后续 2–6s 是当前最大体感短板；Q7-B 已把流式定为发布期复评项。
  但流式会触碰「写入时机/幂等/回放」边界，必须限定在独立端点、只影响 LLM 渲染层。
- 被否选项：① `EventSource`（无法带请求头/幂等键、只能 GET）；② `?stream=true` 复用 `/turns`——
  会让同一端点两套响应形状，契约测试与前端校验复杂度上升；③ 阶段 1 直接默认开启——golden/e2e 与
  离线确定性不稳。
- 影响面：`agents/narrator`/`llm` 客户端（若支持增量）、`api/routes/turns.py`、`web` 对局页与 client。
- 回写落点：第 8/12/23 章 + `docs/design`（流式协议）、ADR D-N2-1（037 交付时补细节）。
- 验收断言：同步 `/turns` 全量旧测试零改动；流式端点新增测试；e2e 至少 1 步验证流式/回退；`demo/console
  --check` 逐字不变。

### D-N5 场景 DSL v2 / 编辑器 / 分享边界（N1 029–032）

- 决策：DSL v2 在 v1 白名单谓词上增加 **flag/quest/物品/NPC 状态/时间条件** 与 **多结局选择**，
  仍为纯数据 + 白名单求值（无 eval/脚本/表达式）；`schema_version=2` 需向前兼容读取 v1；编辑器只产出
  JSON 并实时调用服务端 `/scenarios/validate`，**不旁路校验、不直写库**；分享 = 单文件场景包交换
  （导出/导入），不做云端托管/账号/市场。
- 理由：用户「剧情固定 → 自己上传 JSON」的诉求已在 v1 满足；下一步自然扩展是让玩家少写 JSON（编辑器）
  与交换内容（分享）。但「执行用户内容」是安全红线，扩展条件语义必须保持可静态校验、可确定性回放。
- 被否选项：① 用 JS/Python 表达式做条件——不可静态校验、不可回放、安全红线；② 云端场景市场——需账号/
  存储/审核，超出单机范围；③ 编辑器直接写 `scenarios` 表——绕过统一校验与幂等。
- 影响面：`domain/user_scenario.py`、`api/routes/scenarios.py`、`web/src/views/Scenario*`、示例 JSON。
- 回写落点：`docs/design/scenario-dsl-v2.md`（029 产出）、`docs/design/user-scenario-modules.md`、第 6/23 章。
- 验收断言：v1 旧例零改动；v2 解析/求值单测 ≥25；非法 JSON/未知谓词给结构化 errors；编辑器 e2e 步骤。

### D-N6 跑团世界模组是唯一允许新增 EventType 的轨道切片

- 决策：跑团世界模组 P0（N1 033–034）需要「线索/手札揭示状态持久化」，必须写事件，因此是该计划中
  **唯一允许新增 `EventType`** 的切片，且必须：① 单独立 ADR（D-N1-2）并由用户拍板；② 同步 reducer/
  `GameState` 派生/回放/快照/schema 校验；③ 新旧 golden 双跑对比，旧 4 场景 golden 作为「未触发新事件」
  分支保持逐字不变；④ GM 层内容永不进 `/view`/prompt/事件 payload。
- 理由：另案设计文档（`docs/design/trpg-world-module.md`）已论证「揭示必须是事件」；把该例外显式限定在
  一个切片，避免其他轨道顺手加事件类型破坏既有 golden。
- 被否选项：① 用现有事件类型拼接（无合适语义，会污染审计/回放）；② 把揭示状态放内存/渲染时计算——
  刷新/重连/回放即丢，违背「揭示必须持久」。
- 影响面：`domain/events.py`、reducer、`GameState` 派生视图、回放 golden、模组数据层。
- 回写落点：D-N1-2 ADR、第 5/11/14 章、`docs/design/trpg-world-module.md`。
- 验收断言：新增事件类型只增不改；旧 golden 零改动；新 golden 逐字段断言；未揭示内容泄漏测试为 0。

### D-N7 明确不做清单

- 决策：账号体系/云存档/多用户/在线市场；LLM 成本计费与 `llm_call_log`（D-M5-10）；世界书 `vectorized`/
  `outlet`/`characterFilter`（无宏/无 embedding 设计决定）；用户内容内执行脚本/表达式；默认引入 Playwright
  长期 CI 矩阵（055 只评估）；PyPI 正式发布（D-N3 留待用户拍板）。
- 理由：与单机单用户、零新增依赖、确定性回放的既有产品/技术定位一致；避免计划表变成无限扩张的愿望清单。
- 影响面：第 17 章 §17.9.5、风险表（R-T12 收窄）、README 限制段。
- 回写落点：第 17 章 §17.9.5、第 20 章风险状态注记。
- 验收断言：后续批次若要做以上项，必须先改本节并新增 ADR，否则文档门禁/评审可拒。
