### 17.2 各里程碑交付物与验收标准
#### M1 骨架（001–004）
目标：一个没有业务功能、但“事件 → 回放”链路可复现的骨架。交付物：`src/textgame/` 目录与三层依赖分组、`domain/models.py`+`results.py`+`events.py` 最小实现、EventLog 内存实现与快照雏形、import-linter/ruff/mypy/pytest 的 CI 基线、`docs/progress/` 首篇文档与 `docs/PROGRESS.md` 更新。
验收标准（可测）：
- [ ] `uv run pytest -q` 通过；`GET /healthz` 返回 200；`uv run lint-imports` 通过。
- [ ] `Result`/`ErrorCode` 的 8 个错误码有单测；`GameState` 可序列化/反序列化。
- [ ] 追加 1 条 Event 后按 `rng_seed` 重放，`state_hash` 与预期一致。
- [ ] CI 同时跑 Python 3.10 与 3.12（3.10 只跑核心单测，见第 18 章）。

#### M2 单场景 MVP（005–009）
目标：单房间、单角色、解析 → 判定 → 叙事 → 提交的完整回合。交付物：`POST /game/{id}/turn`、解析/裁判/叙事三类 Agent、RuleEngine + RandomSource、SQLite 事件表/快照表、replay CLI、首个 golden 回放用例。
验收标准：
- [ ] 连续 5 回合端到端可玩，每屏文本 80～150 字；非法输入返回 `INVALID_INPUT`/`NOT_ALLOWED` 等错误码且零状态变更。
- [ ] 同一 `rng_seed` + 同一输入序列回放，`state_hash` 一致（golden 测试）。
- [ ] 解析 Agent 输出经 JSON Schema 校验；用 FakeLLM 断言“校验失败 → 一次修复重试 → 澄清/确定性兜底”三分支。
- [ ] 进程重启后从快照恢复并对齐回合号；M2 覆盖率目标 overall ≥80%（与第 18 章 18.7 一致）。

#### M3 多角色（010–014）
目标：多角色各挂一个角色 Agent，世界仍只有一个写入者。交付物：`PerceptionSlice`、`actor_scope` 工具可见性、ProposalQueue、Resolver、GameEngine CAS 提交、冲突审计查询。
验收标准：
- [ ] 两个 NPC 同回合提交冲突提案，Resolver 统一裁决（Resolution）且仅一个生效，`Resolution` 记录 verdict/reason。
- [ ] 越权测试全绿：角色 A 的 Agent 无法获得 B 的私有记忆、隐藏物品或 destructive 工具（0 泄漏）。
- [ ] 并发提交触发 CAS 冲突时返回 `CONFLICT` 并整体回滚，事件序号连续无空洞。
- [ ] 10 回合多角色回放 `state_hash` 一致。

#### M4 制造（015–018）
目标：常规制造完全确定性，自由制造必须过校验。交付物：配方数据模型、`calculate_craft_result`、CraftService、craft Agent 的 Schema 与状态一致性检查、失败回滚与审计。
验收标准：
- [ ] 常规配方 100% 走确定性路径，同 seed 同输入结果一致。
- [ ] 自由制造输出必须过 JSON Schema + 状态一致性（材料存在/数量/解锁条件）；不合法输出回滚且状态不变。
- [ ] 5 个制造 golden 回放用例一致；失败分支有专门用例覆盖。

#### M5 API 调用治理（019–024）
目标：所有模型调用经 LLMClient，任何未校验输出不得写入状态。交付物：LLMClient（超时/指数退避/限流/幂等键/日志/token 计量/成本归集/供应商回退）、模型分级与缓存、Schema 修复重试与确定性兜底、批量合并与休眠策略、供应商故障演练。
验收标准：
- [ ] 故障注入下供应商 A → B 回退成功；相同幂等键重复请求只产生一次副作用。
- [ ] 红队样本集（n≥50）中非法模型输出 0 次进入状态；修复重试次数可统计。
- [ ] 成本报表可按 Agent、按回合拆分；单回合调用次数/成本/延迟有实测对比（串行 vs 合并、缓存命中率）。
- [ ] 全部 LLM 相关测试用录制回放（cassette）或 FakeLLM，不依赖真实网络。

### 17.4 依赖顺序与建议排期
关键路径是 M1 → M2 → M3：M3 的冲突消解依赖 M2 的单回合闭环；M4 只依赖 M2 的配方/背包能力，可与 M3 并行；M5 依赖 M2 的 LLMClient v0，也应尽早与 M3/M4 并行，否则多角色阶段会被调用治理债拖住。2027-02-08 ~ 02-12 留作整体验收与文档回填（第 16–19 章与第 22 章模板对齐）。排期按 2 人后端 + 1 名兼职测试估算；若只有 1 人，建议砍 M5 的批量合并（023）与缓存（020）到 MVP 之后。

**拼接边界**：pytest 只是“证据生成器”，验收标准必须写成可执行断言，不接受“人工点过”；`--junitxml` 输出作为进度文档的证据链接。uv 与 pytest/pre-commit 均为 dev 依赖，不进运行时镜像；验收机器一律 `uv sync --frozen`，禁止在本地临时 `pip install` 污染基线。失败模式：工具链升级导致 M2 验收基线漂移 → 工具版本进 dev 组并锁定，升级只允许在里程碑切换点进行并重跑全部 golden 用例。

### 本章结论
1. M1–M5 编号与区间 001–004、005–009、010–014、015–018、019–024 与第 22 章 22.3 的编号映射一致，共预留 24 篇进度文档，M1–M5 主题清单已给出可直接抄用的任务表。
2. 关键路径 M1→M2→M3；M4 与 M5 都只依赖 M2，建议与 M3 并行，否则多角色联调会被 LLM 治理债拖慢。
3. 验收标准必须可执行：每个里程碑至少 3 条命令/断言级判据，证据由 pytest `--junitxml` 输出并挂进进度文档。
4. 排期建议：2026-11-09 启动，M1 2 周、M2 3 周、M3 4 周、M4 3 周（并行）、M5 8 周（并行），2027-02-12 前完成整体验收。
5. 可执行建议：M1 第一篇进度文档（001）就固定“验收证据表”格式与 CI 命令，后续 23 篇直接复用，避免第 22 章模板与真实实践脱节。
