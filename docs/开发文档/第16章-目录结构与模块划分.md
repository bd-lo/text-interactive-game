### 16.2 依赖方向与自动化约束
依赖方向与第 4 章一致，只允许自上而下：`api → orchestration → agents/tools → services → domain`；`persistence` 实现 `services` 声明的仓储接口，`domain` 不依赖任何外层（含不 import `pydantic-settings`、`sqlalchemy`）。三条硬规则：

1. 供应商 SDK 只能出现在 `llm/providers.py`；`api/`、`services/` 中出现 `litellm`/`openai` import 即架构违规。
2. `langgraph` 只允许出现在 `orchestration/`；StateGraph 的 checkpointer 不得替代 EventLog（状态权威见第 11、14 章）。
3. `persistence/` 不得 import `services/` 的具体实现，只能被 `services/game_engine.py` 与 `main.py` 使用。

用 import-linter（BSD-2-Clause，3.10 锁 2.15）把上述规则变成 CI 门禁，配置写在 `pyproject.toml`：
```toml
[tool.importlinter]
root_package = "textgame"

[[tool.importlinter.contracts]]
name = "分层依赖（只允许自上而下）"
type = "layers"
layers = [
  "textgame.api",
  "textgame.orchestration",
  "textgame.agents | textgame.tools",
  "textgame.services",
  "textgame.domain",
]

[[tool.importlinter.contracts]]
name = "domain 不得依赖框架与 IO"
type = "forbidden"
source_modules = ["textgame.domain"]
forbidden_modules = ["fastapi", "sqlalchemy", "litellm", "langgraph", "textgame.llm", "textgame.persistence"]
```
失败分支：`uv run lint-imports` 退出码非 0 → CI 阻断；确需例外时只允许在契约里写 `ignore_imports` 并附理由与到期日，禁止用 `# noqa` 绕过。tach（MIT）能力重叠，仅作参考设计，M1 不引入第二套边界检查工具。

### 16.3 模块职责与「依赖 / 拷贝 / 适配 / 自建」标注
| 模块 | 职责 | 标注 | 具体来源与边界 |
| --- | --- | --- | --- |
| `api/` | HTTP 路由、DTO、鉴权、幂等键透传、错误码映射 | 依赖 | FastAPI 0.162.x + Pydantic 2.14.x；不写状态、不调模型 |
| `domain/models.py`、`results.py`、`events.py` | 领域模型、Result/ErrorCode、Event 结构 | 自建 | 只借 Pydantic v2 的校验与序列化；字段名按第 5 章 5.2–5.5 |
| `domain/rules/`、`domain/crafting.py` | 骰子、判定、掉落、伤害、确定性制造 | 自建 | 纯函数，无 IO/无 LLM，复用模式见第 10、13 章 |
| `services/` | 查询/背包/角色/判定/动作/制造/事件日志的可信 API | 自建 | 返回 `Result`；不 commit，不直接改 GameState |
| `services/game_engine.py` | 唯一写入者：CAS 校验 + 原子提交 + 事件落盘 | 自建 | 参考 Text-Game-Engine 的三段事务与 CAS（MIT，只参考不拷贝，第 11 章） |
| `tools/` | @tool 注册、JSON Schema、白名单、actor_scope、side_effect | 自建 | 参考 ToolRegistry 的 tag 权限与 Schema 生成设计（第 7 章裁定）；`actor_scope` 语义必须与 Resolver 门对齐，故不直接 pip 依赖 |
| `agents/` | 六类 Agent 的输入/输出与 Prompt 组装 | 自建 | 只接收 `PerceptionSlice`；LLM 调用统一经 `llm/` |
| `orchestration/` | TurnOrchestrator、ProposalQueue、Resolver | 自建 | LangGraph 仅作为包内可选依赖（`graph.py`），不承载状态 |
| `llm/` | LLMClient 封装、校验与修复重试、成本归集 | 适配 | 对外固定 `LLMClient` 接口，内部依赖 LiteLLM 1.108.x + tenacity 9.2.x；instructor 1.17.x 作为运行时依赖（仅 llm/ 内部的结构化修复重试），与第 12 章一致 |
| `persistence/` | ORM 表、仓储、快照、replay | 依赖 | SQLAlchemy 锁 `>=2.0.57,<2.1`（2.1 起要求 Python ≥3.11）；Alembic 管迁移 |
| `config/` | 配置与随机种子策略 | 依赖 | pydantic-settings 锁 2.15.0（2.16 起要求 ≥3.11） |
| `main.py`、`api/app.py` | 依赖组装与进程入口 | 自建 | 组合根（Composition Root），唯一允许跨层 new 对象的位置 |
| `tests/`、`docs/` | 测试与进度文档 | 自建 | pytest 生态与 `docs/progress` 制度（第 17、18、22 章） |

标注映射：依赖 ≈ pip 依赖；拷贝 ≈ 拷贝代码；适配 ≈ 协议对接或 pip 适配层；自建 ≈ 不引入外部仓库（对应四种方式中的“放弃”，由本仓库实现）。

**拼接边界（一）：依赖只分三层**。runtime 依赖（FastAPI、Pydantic、SQLAlchemy、LangGraph、LiteLLM、tenacity）进 `[project.dependencies]`；开发工具（uv、ruff、mypy、pytest、pre-commit、import-linter）进 dev 依赖组或独立二进制，**不进运行时镜像**；架构检查工具只校验不运行，M1 起即在 CI 生效。

**拼接边界（二）：模板只抄形状不抄栈**。full-stack-fastapi-template 的 `frontend/` 是 Node 工具链，违反技术栈硬约束，不引入；只参考其 `backend/app/` 的“api/core/models”分层与测试目录习惯。本项目持久化从 SQLite 起步，不引入 Postgres/Docker 编排（M1 仅需 `uv run uvicorn` 可跑）。

**拼接边界（三）：工具层自建的理由**。ToolRegistry 的 tag 权限模型（READ_ONLY/DESTRUCTIVE/NETWORK）与本项目 `side_effect` 几乎同构，但其 `actor_scope` 只解决“可见性”，不解决“该调用是否必须经 Resolver 裁决”，这一层必须在本仓库实现（第 7 章）；因此 ToolRegistry 只作设计参考，不 pip 依赖，避免两套权限语义。本章不存在「拷贝代码」与「协议对接」两类拼接：工具层、回合引擎与服务层代码全部自写；MCP/OpenAPI 的外部工具服务对接留到 M3 之后再评估（边界见第 7 章）。

### 16.6 待定与回填
- **GameEngine 代码位置：定稿为方案 A `services/game_engine.py`**。理由：其依赖只有 `domain` 与仓储接口，放服务层依赖方向最顺；`orchestration/` 只负责调用，不持有写入权。第 4 章已完成回填（表格与目录树均采用 `services/game_engine.py`，方案 A）。
- **待定：回放 CLI 的落点**。方案 A：`persistence/replay.py` 的 `python -m` 入口（少一个包）；方案 B：独立 `cli/` 包（未来加 `seed`、`event-tail` 等运维命令更整齐）。取 A 起步，M5 若运维命令超过 3 个再拆 B。

### 本章结论
1. 目录按本章 16.1 与第 4 章 4.2 的分层定稿，新增文件只做“包内展开”，不改顶层结构；`services/game_engine.py` 为唯一写入者（第 4 章已按方案 A 回填）。
2. 依赖方向用 import-linter 的 `layers` + `forbidden` 契约在 CI 强制，`domain` 不得 import 任何框架、IO 与 `llm/`；契约失败即阻断合并。
3. 模块标注结论：接入/持久化/配置/`llm/` 为“依赖或适配”，领域、服务、工具、编排、智能体为“自建”；工具层参考 ToolRegistry 但不引入其权限实现。
4. 开发环境统一 `uv sync --frozen` + Python 3.12 运行时、源码兼容 3.10；`SQLAlchemy<2.1`、`pydantic-settings==2.15.*` 是 3.10 环境的两条硬锁定。
5. 可执行建议：M1 第一个 PR 就加入 `pyproject.toml` 三层依赖分组、`lint-imports` CI job 与 `.pre-commit-config.yaml`，避免架构债后补。
