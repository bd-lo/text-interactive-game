### 16.2 依赖方向与自动化约束
依赖方向与第 4 章一致，只允许自上而下：`api → orchestration → agents/tools → services → domain`；`persistence` 实现 `services` 声明的仓储接口，`domain` 不依赖任何外层（含不 import `pydantic-settings`、`sqlalchemy`）。四条硬规则：

1. 供应商 SDK 只能出现在 `llm/providers.py`；`api/`、`services/` 中出现 `litellm`/`openai` import 即架构违规。
2. `langgraph` 只允许出现在 `orchestration/`；StateGraph 的 checkpointer 不得替代 EventLog（状态权威见第 11、14 章）。
3. `persistence/` 不得 import `services/` 的具体实现，只能被 `services/game_engine.py` 与 `main.py` 使用。
4. Web 客户端（`web/`）只能通过 `/api/v1` HTTP 契约访问后端，不 import Python 包、不持有权威状态；写操作必须带 `Idempotency-Key`，提交仍由后端 Resolver/GameEngine 完成。SPA 深链回退由后端负责：`/api` 之外的未命中路径返回 `index.html`（catch-all），否则 `/cards/:id`、`/games/:id/replay` 刷新 404（第 23 章）。

用 import-linter（BSD-2-Clause，3.10 锁 2.15）把上述规则变成 CI 门禁，配置写在 `pyproject.toml`：
```toml
[tool.importlinter]
root_package = "textgame"

[[tool.importlinter.contracts]]
name = "分层依赖（只允许自上而下）"
type = "layers"
layers = [
  "textgame.api",
  "textgame.orchestration",
  "textgame.agents | textgame.tools",
  "textgame.services",
  "textgame.domain",
]

[[tool.importlinter.contracts]]
name = "domain 不得依赖框架与 IO"
type = "forbidden"
source_modules = ["textgame.domain"]
forbidden_modules = ["fastapi", "sqlalchemy", "litellm", "langgraph", "textgame.llm", "textgame.persistence"]
```
失败分支：`uv run lint-imports` 退出码非 0 → CI 阻断；确需例外时只允许在契约里写 `ignore_imports` 并附理由与到期日，禁止用 `# noqa` 绕过。tach（MIT）能力重叠，仅作参考设计，M1 不引入第二套边界检查工具。

**拼接边界（一）：依赖只分三层**。runtime 依赖（FastAPI、Pydantic、SQLAlchemy、LangGraph、LiteLLM、tenacity）进 `[project.dependencies]`；开发工具（uv、ruff、mypy、pytest、pre-commit、import-linter）进 dev 依赖组或独立二进制，**不进运行时镜像**；架构检查工具只校验不运行，M1 起即在 CI 生效。

**拼接边界（二）：模板只抄形状不抄栈**。full-stack-fastapi-template 的 `frontend/` 是 Node 工具链，不引入；只参考其 `backend/app/` 分层与测试目录。持久化从 SQLite 起步，不引入 Postgres/Docker 编排（M1 仅需 `uv run uvicorn`）。

**拼接边界（三）：工具层自建的理由**。ToolRegistry 的 tag 权限模型（READ_ONLY/DESTRUCTIVE/NETWORK）与本项目 `side_effect` 几乎同构，但其 `actor_scope` 只解决“可见性”，不解决“该调用是否必须经 Resolver 裁决”，这一层必须在本仓库实现（第 7 章）；因此 ToolRegistry 只作设计参考，不 pip 依赖，避免两套权限语义。本章不存在「拷贝代码」与「协议对接」：工具层、回合引擎与服务层全部自写，MCP/OpenAPI 外部工具对接留到 M3 后（见第 7 章）。

### 16.5 开发环境与启动命令
```bash
uv python install 3.12          # 运行时建议 3.12（3.10 已于 2026-10-01 EOL，见第 19 章）
uv sync --frozen                # 严格按 uv.lock 安装（runtime + dev）
uv run pre-commit install --install-hooks
uv run uvicorn textgame.main:app --reload --port 8000   # POST /api/v1/turns
uv run ruff format --check . && uv run ruff check .

uv run lint-imports
uv run pytest -q
uv run python -m textgame.persistence.legacy_upgrade --db-url sqlite:///data/textgame.db   # 旧库升级（回放由 tests/replay/ 承担）
# 前端（Node 仅构建期；运行时不依赖 Node）
pnpm --dir web install --frozen-lockfile
pnpm --dir web build            # → web/dist
```

| --- | --- | --- |

**构建与托管流水线**：`pnpm --dir web build` 生成 `web/dist` → `create_app()` 先注册 `/api/v1` 路由，再挂载 `StaticFiles(directory="web/dist", html=True)`；注意 `html=True` 只处理目录索引与缺失文件，**不做 SPA 深链回退**，因此必须再注册 catch-all：非 `/api` 前缀且未命中静态文件的请求返回 `index.html`（前端 history 路由），否则 `/cards/:id`、`/games/:id/replay` 一刷新就 404。`web/dist` 缺失时跳过静态挂载（API 照常可用），构建失败则 CI `web-build` 阻断发布。产物为纯静态文件，运行时不需要 Node/pnpm；依赖与 Node pin 见 19.7（Node 24.x LTS 仅构建期）。

### 本章结论
1. 目录按本章 16.1 与第 4 章 4.2 的分层定稿，新增文件只做“包内展开”，不改顶层结构；`services/game_engine.py` 为唯一写入者（第 4 章已按方案 A 回填）。
2. 依赖方向用 import-linter 的 `layers` + `forbidden` 契约在 CI 强制，`domain` 不得 import 任何框架、IO 与 `llm/`；契约失败即阻断合并。
3. 模块标注结论：接入/持久化/配置/`llm/`/`web/` 为“依赖或适配”，领域、服务、工具、编排、智能体为“自建”；`web/dist` 为静态产物、Node 仅构建期；工具层参考 ToolRegistry 但不引入其权限实现。
4. 开发环境统一 `uv sync --frozen` + Python 3.12 运行时、源码兼容 3.10；`SQLAlchemy<2.1`、`pydantic-settings==2.15.*` 是 3.10 环境的两条硬锁定。
5. 可执行建议：M1 第一个 PR 就加入 `pyproject.toml` 三层依赖分组、`lint-imports` CI job 与 `.pre-commit-config.yaml`，避免架构债后补。
