### 10.1 判定优先级：规则优先，智能体兜底

判定分五级，默认走到 L2 就结束；L3 只在规则确实空白时使用，且必须在 `Resolution` 中写明理由：

| 级别 | 内容 | 执行者 | 是否调模型 | 说明 |
| --- | --- | --- | --- | --- |
| L0 硬约束 | 可见性、所有权、背包容量、状态互斥 | `RuleEngine` 前置检查 | 否 | 不满足直接 `rejected` |
| L1 确定性公式 | 命中、伤害、掉落、技能成功率 | `Ruleset` + `RuleEngine` | 否 | 纯函数，可单测 |
| L2 掷骰 | 在 L1 结果上叠加骰子与难度 | `RandomSource` | 否 | 种子可复现 |
| L3 智能体兜底 | 规则未覆盖的模糊裁决 | `JudgeAgent`（强模型） | 是 | 只给倾向与理由，不给数值；需 `resolution_policy=agent_assisted` |
| L4 人工 | 作者/调试改写 | 后台工具 | 否 | 必须留审计事件 |

“默认判定策略确定性，智能体覆盖需显式理由”落到实现上是三个字段：`Resolution.reason` 必填、`JudgeOutput.evidence_refs` 必须引用感知切片中的实体、`confidence < 0.7` 时 `Resolver` 强制改为保守结果（无有利效果）。

### 10.2 骰子、难度与判定结果结构

判定中的骰子（Dice Roll）统一采用 d20 体系（2G 文字冒险足够，且易于解释）：`total = d20 + 属性修正 + 技能修正 + 环境修正`；自然 20/自然 1 单独判定大成功/大失败；难度（DC）档位固定为 5/10/15/20/25。

| 难度 | DC | 典型场景 |
| --- | --- | --- |
| 琐碎 | 5 | 点灯、辨认明显脚印 |
| 简单 | 10 | 攀爬矮墙、听懂方言大意 |
| 普通 | 15 | 潜行绕过守卫 |
| 困难 | 20 | 撬开铁锁、说服敌对 NPC |
| 极难 | 25 | 无工具拆解机关 |

判定结果 `CheckResult`/`DiceRoll`/`Modifier` 以第 5 章 5.6 定稿为准（归属 `domain/rules/types.py`，含 `rng_seed` int64 约束 `0 ≤ rng_seed ≤ 2**63-1`），本章不重复定义；字段用途见下方示例。

示例（种子由 `RandomSource.derive_seed(save_seed="demo-save-2026", turn_id=43, actor_id="player_1", method="sneak_move", seq=50)` 派生并掩码到 63 位）：

```json
{
  "rule_id": "stealth.sneak_v1", "actor_id": "player_1", "target": "guard_a",
  "dc": 15, "dice": [{"sides": 20, "rolls": [12], "kept": [12]}],
  "modifiers": [{"source": "dexterity", "value": 3}, {"source": "darkness", "value": 2}],
  "total": 17, "outcome": "success", "rng_seed": 853400723015425181
}
```

所有骰子结果必须在 `Event.result` 中保留 `dice` 与 `rng_seed`，否则回放无法复算；智能体不得生成或修改骰值。

### 10.3 可复现随机：RandomSource 与 rng_seed

MVP 采用**派生式无状态随机**：不维护全局可变 RNG，每个事件用“存档种子 + 回合 + 角色 + 方法 + 序号”派生子种子，回放时按同样输入重算。`RandomSource.derive_seed()` 内部经 `RandomSource.mask_seed()` 掩码到 63 位（`& 0x7FFF_FFFF_FFFF_FFFF`），返回值满足 `0..2**63-1`，与第 5 章 `Event.rng_seed` 字段约束、PostgreSQL/SQLite 的 `BIGINT` 上界一致，否则会写库溢出。这样 `GameState.rng_state` 的语义固定为 `{"mode": "derived", "save_seed": "...", "last_seq": n}`（与第 14 章快照格式同步），不必快照 Python 的随机状态。

```python
class RandomSource(Protocol):
    """派生式随机：类方法负责派生与掩码，实例负责掷骰。"""

    @staticmethod
    def mask_seed(raw: int) -> int:
        return raw & 0x7FFF_FFFF_FFFF_FFFF   # 0..2**63-1（Event 与 BIGINT 约束）

    @classmethod
    def derive_seed(cls, save_seed: str, turn_id: int, actor_id: str,
                    method: str, seq: int) -> int:
        """同一 (save_seed, turn_id, actor_id, method, seq) 必得同一已掩码子种子。"""
        key = f"{save_seed}|{turn_id}|{actor_id}|{method}|{seq}".encode("utf-8")
        raw = int.from_bytes(hashlib.blake2b(key, digest_size=8).digest(), "big")
        return cls.mask_seed(raw)

    def randint(self, a: int, b: int) -> int: ...
    def choice(self, seq: Sequence[T]) -> T: ...

class DerivedRandom:
    def __init__(self, seed: int) -> None:
        self._rng = random.Random(seed)
    def randint(self, a: int, b: int) -> int:
        return self._rng.randint(a, b)
```

约束：

1. 游戏逻辑内禁止直接使用 `random.random()`、`np.random`、`secrets`，必须经由 `RandomSource`；
2. 每条 `Event` 必带 `rng_seed`，且满足 `0 <= rng_seed <= 2**63-1`（由 `RandomSource.mask_seed()` 保证）；`result` 中写回骰面，便于跨版本核对；
3. `Ruleset` 带 `ruleset_version` 与 `rule_id`，事件记录版本号，规则修改后旧存档按旧版本重放（第 14 章展开）；
4. 回放验收：同一存档种子重放 1000 回合，逐事件比对 `params/result/rng_seed` 的哈希必须完全一致。

待定项（rng_state 语义，2～3 方案）：A 派生式 + `save_seed`/`last_seq`（推荐，回放最稳、无调用顺序耦合）；B 保存 `random.getstate()` 全状态（兼容旧代码，但 RNG 调用顺序变化即失效）；C 混合（战斗用 A、掉宝用 B）。M2 选 A，若未来出现无法派生的第三方随机源再评估 C。

### 10.4 规则表达选型：Python 函数还是 DSL

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| A. Python 函数 + 数据驱动表 | 类型检查、可单测、无解释器开销、直接调用服务层 | 改规则要发版，策划不能独立改 | MVP 默认 |
| B. 受限 DSL（YAML/JSON 表达式） | 策划可改、可热加载、审计友好 | 需要解析器/校验器与沙箱；表达力不足时被迫扩语言 | M4 之后评估 |
| C. 嵌入非图灵完备规则引擎（参考 YARE） | 边界清晰、天然防死循环 | 引入额外规范与学习成本；无可直接依赖的 Python 包 | 参考设计 |

结论：MVP 用 A——规则以 `Ruleset` 数据（难度表、伤害表、掉落表）+ Python 纯函数实现；只在“规则需要频繁由策划调整且变化可枚举”时再引入 B，且 DSL 只允许白名单运算，不引入图灵完备脚本。MnesOS 的 YARE 证明“把全部状态变更与 RNG 关进规则引擎、LLM 只做叙事”这条边界可行，但其规范在仓库内（`docs/yare-specification.md`），无独立 Python 包可依赖，故只作为参考设计。

### 10.5 三个项目的确定性机制评估

- **Text-Game-Engine**：确定性来自 `row_version` CAS 提交与唯一 `(campaign_id, actor_id)` 在途回合租约，回放时以快照 + 事件为准并用水位限制记忆可见范围；它解决的是“并发提交”的确定性，不解决“数值计算”的确定性，故可作为第 11 章的 CAS/租约参考，不能替代本项目的 `Ruleset`。
- **MnesOS**：YARE 规则引擎把状态变更、数学与 RNG 全部移出 LLM，叙事与机制之间有“气隙”隔离，事件树支持分支时间线；这是本项目“确定性判定 + 叙事包装”最接近的参考。但该项目无许可证文件、要求 Python 3.12+，不能依赖或拷贝。
- **tldw_server**：`reducer.py` 是纯事件到投影的函数、`dice.py` 提供可注入随机源用于测试、`authority.py` 区分直提交与提案；这三点与“事件溯源 + 唯一写入者 + 可复现随机”高度同构。但这是实现计划（仓库内 plan 文档），不是成品 API，且 `tldw_Server_API/**` 为 GPL-3.0-only，只能参考设计、不得拷贝进闭源分发。

### 本章结论

1. 判定默认走 L0→L2 确定性链，L3 智能体兜底必须满足三个条件：`resolution_policy=agent_assisted`、`reason` 可审计、`confidence>=0.7`，否则保守裁决。
2. 所有随机由 `RandomSource.derive_seed()`（blake2b）派生、由 `RandomSource.mask_seed()` 掩码到 `0..2**63-1`；`Event.rng_seed` 与骰面必须入库；游戏逻辑禁止直接调用 `random`/`numpy.random`。
3. 规则表达 MVP 选“Python 纯函数 + Ruleset 数据”，DSL 推迟到 M4；不引入 YARE 等外部规范作为运行时依赖。
4. 执行建议：M2 交付固定种子回放测试（1000 回合逐事件哈希一致）与判定单元测试（DC 档位、自然 1/20、修正叠加），作为事件溯源（第 14 章）的验收前置。
5. `CheckResult`/`DiceRoll`/`Modifier` 已定稿于第 5 章 5.6（含 `rng_seed` int64 约束），无需再补；`rng_state` 语义按派生式落地（见 10.3 的三方案），与第 14 章快照格式一起定稿。
