### 1.1 文档目的
《文字交互游戏》从零搭一个复古 2G 文字 MUD 风格的单机/异步游戏。本文件是团队唯一技术执行基线：把「做什么、怎么分层、选哪些轮子、边界在哪、怎么验收」写成可执行条目，覆盖后端、策划、前端与新人。它不是策划案或宣传稿，也不重新讨论已知设计决策——与 1.4 规则及第 4 章架构冲突的写法先修正再实现。**v0.3 起开发模式采用 vibe coding：AI（编码智能体）主导编码，人类负责拆任务、给上下文、跑验收与 review；开发计划见第 17 章，进度制度见第 22 章。**

### 1.3 如何使用本文档
1. 结论先行：每章末尾「本章结论」即该章决策，正文只是支撑。
2. 拼接方式只用四个词：`pip 依赖`、`拷贝代码`、`协议对接`、`参考设计`（定义见第 4 章 4.5），任何「引入某库」必须标注其一。
3. 接口给 Python 3.10+ 类型注解签名，数据给合法 JSON 示例，可直接抄用。
4. 「待定」须带 2～3 个方案与取舍，开工前写入进度文档；引用其他章节只写「见第 X 章」。
5. 证据口径：仓库数据为 2026-11-08 检索结果；Python 兼容性按 `requires-python` 与 PyPI 元数据核对，未核实写「未能确认」。

### 1.6 术语与证据约定
术语首次出现附英文，完整中英对照见第 21 章；本节先约定 8 个高频词：

| 中文 | 英文 | 一句话定义 |
| --- | --- | --- |
| 回合 | Turn | 玩家一次输入到返回新屏文本的处理单元 |
| 事件溯源 | Event Sourcing | 以不可变事件序列作为状态唯一事实来源 |
| 唯一写入者 | Single Writer | 只有 GameEngine 能提交状态变更 |
| 提案 / 裁决 | Proposal / Resolution | Agent 提提案，Resolver 裁决后提交 |
| 感知切片 | Perception Slice | 每个角色 Agent 可见的局部状态投影 |
| 确定性兜底 | Deterministic Fallback | 模型不可用或输出不合法时的确定性默认结果 |
| 幂等键 | Idempotency Key | 同一请求重复提交只生效一次的标识 |
| 乐观并发控制 | Optimistic Concurrency Control（CAS） | 用版本号校验提交，冲突时最多 3 次尝试（首次 + 2 次重试） |

许可证结论分三档：宽松（MIT、Apache-2.0、BSD）可依赖、可拷贝；传染性（GPL、AGPL）只能参考设计；未声明许可证一律不拷贝。许可证与活跃度须来自实际打开确认（第 4 章），术语展开见第 11、14、21 章。
