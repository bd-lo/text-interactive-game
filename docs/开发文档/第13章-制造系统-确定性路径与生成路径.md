### 13.1 结论先行
制造是**两个系统**：常规配方走纯函数 `calculate_craft_result`，全程不调用 LLM；只有「无匹配配方 + 玩家明确描述组合 + 自由制造开关打开 + 预算允许」四条件同时成立，才触发制造 Agent 生成草案（`CraftOutput`→`CraftDraft`，校验通过后形成 `CraftProposal`）。生成路径只允许 LLM 给性质、命名、描述与效果 ID，**所有数值由框架重算**，LLM 给的任何数字一律丢弃。

### 13.2 配方数据模型与制造域契约类型
制造域契约类型统一由本章定义（第 5 章 5.6 表引用本章，避免全队出现未定义类型）；命名链为第 8 章 `CraftOutput`（Agent 原始输出）→ 本章 `CraftDraft`（规范化草案）→ 本章 `CraftProposal`（校验通过后交 Resolver 的领域提案），`CraftRequest` 为服务层入参（第 6 章）。最小契约定义如下：

```python
class CraftMode(str, Enum):
    RECIPE = "recipe"   # 有配方：确定性 calculate_craft_result
    FREE = "free"       # 无配方：CraftAgent 生成草案

class CraftRequest(BaseModel):
    mode: CraftMode
    recipe_id: str | None = None          # RECIPE 必填
    free_description: str | None = None   # FREE 必填（玩家原话，≤200 字）

class CraftInput(BaseModel):
    item_id: ItemId
    qty: int = Field(ge=1)
    role: Literal["material", "tool", "catalyst"]

class QualityBand(BaseModel):
    min_roll: float = Field(ge=0.0, le=1.0)
    quality: Literal["poor", "common", "fine", "masterwork"]

class Byproduct(BaseModel):
    item_id: ItemId
    qty: int = Field(ge=1)
    chance: float = Field(ge=0.0, le=1.0)

class CraftStateSlice(BaseModel):
    """calculate_craft_result 的确定性输入：只含本次制造所需视图。"""
    actor_id: CharacterId
    inventory: dict[ItemId, int]
    skill_levels: dict[str, int]
    station_id: str | None = None

class CraftResult(BaseModel):
    ok: bool
    success: bool
    consumed: list[CraftInput]
    produced: list[CraftInput]
    byproducts: list[Byproduct] = Field(default_factory=list)
    quality: str | None = None
    rng_seed: int = Field(ge=0, le=0x7FFF_FFFF_FFFF_FFFF)
    reason: str | None = None

class CraftDraft(BaseModel):
    """CraftOutput 规范化后的草案：只含名称/材料/工位/步骤，禁止数值字段。"""
    item_name: str = Field(min_length=1, max_length=30)
    output_item_id: str | None = None
    inputs: list[CraftInput]
    station: str | None = None
    steps: list[str] = Field(default_factory=list, max_length=8)

class CraftProposal(BaseModel):
    """校验通过、交给 Resolver 的领域提案。"""
    proposal_id: str
    actor_id: CharacterId
    turn_id: int
    reason: str
    proposed_recipe: dict
    narrative_hint: str | None = None
```
配方与确定性输入模型：
```python
class Recipe(BaseModel):
    recipe_id: str
    name: str
    version: int = 1
    inputs: list[CraftInput]
    output_item_id: str
    output_qty: int = 1
    station: str | None = None
    skill_req: dict[str, int] = Field(default_factory=dict)
    base_success_rate: float = Field(ge=0.0, le=1.0)
    quality_bands: list[QualityBand]
    byproducts: list[Byproduct] = Field(default_factory=list)
```
配方以 JSON/YAML 存放于 `src/textgame/data/recipes/`，启动时校验并注册进 `CraftService`；`recipe_id` 全局唯一，`version` 变更不允许原地修改，必须新增版本（事件回放要能还原旧配方语义，见第 14 章）。确定性入口签名固定为：

```python
def calculate_craft_result(
    state: CraftStateSlice,
    recipe: Recipe,
    actor_id: CharacterId,
    rng_seed: int,
) -> CraftResult: ...
```
该函数纯函数、无 IO、同一 `rng_seed` 必得同一结果；随机种子由 `RandomSource.derive_seed(save_seed, turn_id, actor_id, method, seq)` 派生（见第 10 章），因此事务回滚时不需要回滚 RNG 状态。`CraftService` 只是服务入口包装：先解析 `ctx`/`recipe_id` 与背包上下文，再调用该领域函数（服务层接口见第 6 章）。

示例配方 JSON：
```json
{"recipe_id":"recipe.iron_sword","name":"铁剑","version":1,
 "inputs":[{"item_id":"item.iron_ingot","qty":2,"role":"material"},
           {"item_id":"item.oak_handle","qty":1,"role":"material"},
           {"item_id":"item.forge_hammer","qty":1,"role":"tool"}],
 "output_item_id":"item.iron_sword","output_qty":1,"station":"station.forge",
 "skill_req":{"crafting":2},"base_success_rate":0.85,
 "quality_bands":[{"min_roll":0.0,"quality":"common"},{"min_roll":0.8,"quality":"fine"}],
 "byproducts":[]}
```

### 13.3 路径切换策略
| 条件 | 走哪条路径 | 记录 |
| --- | --- | --- |
| 有配方，材料/工具/技能全部满足 | 确定性 `calculate_craft_result` | Event `CRAFT_DETERMINISTIC`（含 rng_seed） |
| 有配方，消耗物不足/缺工具/技能不足 | 确定性失败 | Event `CRAFT_REJECTED` + `error_code` |
| 无配方，自由制造开关开且预算允许 | 生成路径（Agent） | Event `CRAFT_GENERATED` + proposal hash |
| 无配方，开关关闭或超预算 | 返回 `NOT_FOUND`（提示「没有可行配方」） | 仅审计事件 |
| 智能体想覆盖确定性结果 | 禁止；只能提交「新配方提案（Proposal）」交 Resolver 裁决（Resolution） | `resolution_policy=agent_assisted` + 显式 reason |

「近似配方」判定**待定**，首版不做：① 精确匹配（推荐，行为可预测）；② 材料替换表（如石头替代铁，需策划维护替换矩阵）；③ 相似度匹配交给 Agent 提议、Resolver 审批（成本高、可解释性差）。

### 13.4 自由制造生成路径
1. 制造 Agent 只接收私有感知切片（Perception Slice）：背包清单、当前房间/工作台、已知配方 ID 列表、玩家原话；不接收全局 GameState（第 9、11 章）。
2. 输出 `CraftOutput`（第 8 章，`CraftAgent` 的原始输出）→ 本层规范化为 `CraftDraft`：`item_name / output_item_id / inputs / station / steps`；Schema 中**不提供任何数值字段**（无 stats、无 damage）。
3. Schema 校验（pydantic strict + jsonschema Draft 2020-12）→ 失败进入一次修复重试；仍失败 → 返回「无法处理」。
4. 状态一致性检查（全部在 `CraftService` 内，失败即拒绝）：材料必须在该角色背包且数量足够；工具/工作台必须存在且可用；`inputs` 只能引用背包内 item_id；效果 ID 必须在白名单内；稀有度不得超过材料等级上限；名称/描述长度限 1～30/1～120 字；不得引用未知实体；不得涉及其他角色所有物。
5. 数值重算：`CraftService` 依据材料强度映射表计算产出 stats，生成路径下 `stats_claim` 字段不存在，出现即 `SCHEMA_VIOLATION`。
6. 校验通过后由 `CraftService` 组装 `CraftProposal` 交 Resolver 裁决；裁决后由 `GameEngine.submit(expected_version, events, idempotency_key)` 原子提交（`CraftService` 不开启/提交事务、不调用 `GameEngine`，只返回含草稿 events 的 `Result`）；Event 记录 `proposal_hash`、`prompt_version`、校验结果、`rng_seed`，便于回放审计。
7. 失败时服务层返回 `Result(ok=false)` 且不带可提交事件，材料与 GameState 的零变更由 `GameEngine` 事务回滚保证（见 13.5）。

示例 `CraftProposal`：
```json
{"proposal_id":"p-0007","actor_id":"char.player_1","turn_id":42,
 "reason":"玩家把火把与铜线绑在木棍上，要求做一个能放电的武器",
 "proposed_recipe":{"name":"简易电击棒","output_item_id":"item.makeshift_taser",
   "inputs":[{"item_id":"item.oak_handle","qty":1,"role":"material"},
             {"item_id":"item.copper_wire","qty":2,"role":"material"},
             {"item_id":"item.torch","qty":1,"role":"catalyst"}],
   "station":"station.workbench"},
 "narrative_hint":"玩家自制"}
```
校验失败的返回示例：
```json
{"ok": false, "error_code": "OUT_OF_RANGE", "data": {"violations": [
  {"path": "proposed_recipe.stats", "rule": "NO_LLM_NUMBERS"}]},
 "message": "数值必须由框架计算，proposal 不允许 stats 字段", "events": []}
```
示例中的 `item.*`、`char.player_1` 等为示意 ID（非 ULID）；真实实现按第 5 章的 ID 规则生成。

### 13.5 失败回滚与提交边界
提交边界固定：`CraftService.craft(...)` 只做校验、数值重算与**草稿事件**组装，返回 `Result(ok=True, events=[草稿 Event], data=CraftResult)`（自由制造路径的 `data` 另带 `proposal_hash`，供 Resolver 与审计使用）；它不写库、不 `session.commit()`、不调 `EventLog.append()`、也不调 `GameEngine.submit()`——服务层与 GameEngine 的边界与第 6 章一致。

真正的事务提交由编排层调用唯一写入者完成：`GameEngine.submit(expected_version, events, idempotency_key)` 在一个事务里依次做 ① 校验 `characters.row_version`（乐观并发控制，Optimistic Concurrency Control，CAS，见第 14 章）→ ② 扣材料、产出入包、更新技能经验 → ③ `EventLog.stamp()` 盖章并追加事件 → ④ 计算 `state_hash` 并提交；任一步失败由 `GameEngine` 回滚整个事务并返回 `CONFLICT`/`INTERNAL`，`CraftService` 只把该 `Result` 透传给调用方，材料与产物零变更。

失败尝试的审计由编排层（不是服务层）负责：状态变更事件随事务回滚，但失败尝试通过独立事务写 `audit_events`（best-effort），记录 `turn_id/actor/method/error_code/proposal_hash`。幂等键 `craft_id` 建唯一索引，防止玩家重复点击导致重复消耗；崩溃恢复依赖 `turns.status=IN_PROGRESS` + inflight 租约（第 14 章），恢复时按已提交事件重放，未提交事务由数据库回滚。

复用判断与拼接边界：evennia 的制造 contrib 无法直接拷贝——它继承 evennia 的 command/object/spawner，搬进来等于引入第二套状态与命令层；只借鉴「配方 = 若干材料 + 工具 → 产物」的匹配结构与 `pre/do/post` 钩子顺序，错误类型 `CraftingValidationError` 映射为我们的 `SCHEMA_VIOLATION` / `OUT_OF_RANGE`。open-tabletop-gm 为 AGPL-3.0，禁止依赖或拷贝，仅借鉴「规则计算与叙事彻底分离」的原则；aequus 停更且模型过简，递归展开算法只有二十行，自行实现更省事。

拼接后边界：`calculate_craft_result` 是唯一数值权威，位于 `domain/crafting.py`，不依赖数据库；`CraftService` 负责校验、数值重算与草稿事件组装，不开启/提交事务、不调 `GameEngine`（提交只能由 GameEngine 在编排层调用链上完成）；生成路径的产物必须先过 Schema + 一致性检查才允许进入 ProposalQueue。失败模式统一为 `Result.error_code`：`NOT_FOUND`（无配方）、`INVALID_INPUT`（数量/参数非法）、`OUT_OF_RANGE`（数值越界）、`NOT_ALLOWED`（工具/技能/越权）、`CONFLICT`（并发 CAS 失败，由 GameEngine 返回）。

### 本章结论
1. 制造双路径按 13.3 的表格硬编码判定，优先级固定为「确定性 > 生成 > 拒绝」，不得由 Agent 自行选择路径。
2. `calculate_craft_result` 是纯函数且为唯一数值权威，签名固定、种子由 `RandomSource.derive_seed(...)` 派生，天然支持回放与回滚。
3. 生成路径只允许 LLM 产出「名称/描述/材料组合/效果 ID」，任何数值字段出现即判 `SCHEMA_VIOLATION`，统计量由框架重算。
4. 制造提交由 `GameEngine` 单事务完成（CAS + 幂等键），`CraftService` 只返回 `Result` 与草稿事件、绝不直接提交；失败零副作用，失败尝试由编排层写独立 `audit_events`，保证审计与回放可查。
5. 配方数据模型从第一版就带 `version` 与质量分档，避免 M4 后期改结构导致旧事件无法回放。
6. 「近似配方」首版不做，作为 M4 后的待定项按三方案评估，不允许在没有验收标准前开放。
