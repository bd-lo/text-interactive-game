### 2.1 产品愿景
做一款「可信的文字世界」：单机为主、可异步推进，玩家用自然语言行动，系统用确定性规则判定，模型只把结果写成 80～150 字的一屏。卖点不是画面，而是三件事：规则算得准、叙事接得住、事后查得清。复古 2G（第二代手机时代、没有图形的小屏文字界面）MUD 的质感——小屏、纯文字、节奏慢但有回味——是表现形式，不是技术复古；底层必须是可测试、可回放（Replay）、可审计的现代架构（见第 4 章）。

### 2.2 核心体验循环
核心循环固定为五步，顺序即第 4 章的分层顺序：

1. **输入**：玩家用自然语言或快捷指令输入一句话（建议 ≤200 字）。
2. **解析**：解析 Agent（Parser Agent）输出 `ActionIntent(action, target, params, confidence)`；JSON Schema 校验失败 → 一次修复重试 → 仍失败则返回澄清文本，不产生任何状态变更。
3. **判定**：RuleEngine 用 Ruleset 与 RandomSource 做确定性判定（骰子（Dice Roll）、难度、成功率全部在框架内计算），模型不得参与数值计算。
4. **叙事**：叙事 Agent（Narrator Agent）把判定结果包装成 80～150 字屏文本；字数或 Schema 校验失败 → 模板兜底并标记 `source=template`。
5. **提交**：GameEngine 原子提交 `Result` 与 `Event`（含 turn_id、actor、method、params、result、rng_seed），随后返回屏文本与状态行。

玩家只看得到第 1 步和第 5 步的输出；第 2～4 步是内部流程，任何失败都转成「世界内的说法」（例如越权动作返回叙事化拒绝文本，错误码只进日志与事件），不允许把 `NOT_ALLOWED`、Schema 报错原样抛给玩家。提交步骤的 CAS 冲突处理见第 11 章。

### 2.3 2G 文字风格约束
- **每屏 80～150 字**（硬性，不含状态行）：UI 端与叙事 Agent 输出端双重校验，超限截断重写，低于下限补一句环境描写。
- **一屏一决策点**：每屏只推进一个动作结果，并给一个可行动的钩子（线索、声响、NPC 反应）。
- **四段式排版**：环境 1～2 句 → 结果 1 句 → 钩子/线索 1 句 → 状态行（HP / 关键物品 / 时间）。
- **禁用项**：emoji、Markdown 富文本、超过 3 句的连续设定倾倒、现代网络用语、第二人称以外的视角跳变。
- **表现力边界**：没有图形与音效，用固定意象替代画面（光、声、气味、温度）；世界事实只能来自规则层与内容库，叙事 Agent 不得自由发明设定（防幻觉，见第 15 章）。
- **回合制 / 异步**：单机默认同步回合；异步推进时玩家离线，世界按计划推进。异步触发方式**待定**，三个方案：(A) 定时器扫描，简单但会有空转成本；(B) 玩家回归时按离线时长结算，最省成本但时间线可能跳变；(C) 事件队列 + 计划到达点，最贴近需求但实现最重。建议 MVP 用 B，M3（多角色）起评估 C。
- **前端渲染要求（v0.2，第 23 章实现）**：UI 用系统无衬线、叙事用系统衬线、指令与 JSON 保留等宽（`--font-ui` / `--font-read` / `--font-mono`）；日间 / 夜间双皮肤（**日间默认**，顶栏「外观」一键切换，见第 23 章 §23.4 / D-UI-3）；逐字显示可关（默认关闭，单字 ≤30ms，遵循 `prefers-reduced-motion`）；每屏 80～150 字（同本节硬约束，前端不得自行截断或把多个回合拼成一屏）；键盘优先（↑/↓ 历史、回车提交、`Ctrl+Enter` 换行、全部操作可键盘完成）；无图片/音频依赖；窄屏单列（最小宽度 320px）。

**玩家体验示例**

输入：`我把火折子点亮，蹲下看墙角的刻痕。`

输出：`火折子的光晃了晃，墙上浮出三道刻痕，像被谁反复描过的“7”。你注意到墙根有新土，空气里有铁锈味。北门缝里透进风声。（HP 12/14 · 火折子 剩 2 回合）`

（约 100 字；一个动作、一个结果、一个钩子、一行状态，无解释性旁白。）

拒绝也必须用世界内语言表达。例如玩家输入 `我杀了他`，系统判定该行动不可行时输出：`你的手停在半空——守夜人没有背对你。他侧过脸，火光把他的影子拉得很长。` 玩家不会看到错误码，但 `Event.result.error_code = NOT_ALLOWED` 会进入事件日志供审计。

### 2.4 内容与节奏约束
- 单场景 5～15 个可交互对象；单屏最多引入 1 个新事实，避免信息过载。
- NPC 单次发言 ≤60 字；同一 NPC 连续 3 轮对话必须有新信息或状态变化，否则触发话题切换。
- 延迟预算以第 12 章 12.8 为权威口径（首版端到端 P95 ≤8 秒；M2 缓存命中路径目标 ≤3 秒），本章不另立数值。两个方案：A 同步等待、超时即降级为确定性文本；B 判定先返回、叙事异步补屏（体验更稳，但需要屏间状态管理）。建议 M2（单场景 MVP）先用 A 的简化版（超时直接模板兜底），M5（API 调用治理）引入 B。
- 世界时间只随事件推进；无事件时不推进、不惩罚玩家离线（异步友好）。
- 内容长度、分级与敏感词规范见第 15 章。

### 本章结论
1. 体验成立的前提是「确定性规则 + 模型只写叙事」，这与 open-tabletop-gm、MnesOS 的实际做法一致，列为架构红线。
2. 每屏 80～150 字是硬约束：叙事 Agent 输出必须做字数校验（超限重写、不足补环境句），校验逻辑进测试（见第 18 章）。
3. 回合制优先、异步后置：MVP 只做同步回合；异步推进建议先用「玩家回归按离线时长结算」，M3（多角色）起评估事件队列方案。
4. 四个参考项目全部只能「参考设计」：Python ≥3.12（Evennia、MnesOS）、AGPL-3.0（open-tabletop-gm）、无 LICENSE 文件（MnesOS）任一条件都不满足依赖或拷贝的前提。
5. 玩家永远看不到错误码，只看到世界内语言；错误码、Schema 状态、模型校验结果只进事件与日志，作为第 15 章审计的输入。
