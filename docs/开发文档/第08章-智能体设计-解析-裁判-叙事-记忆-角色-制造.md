### 8.1 总原则：智能体只提案，不落库

每一次回合推进时，智能体（Agent）在本项目中只有两类动作：**输出结构化提案**（Proposal）与**输出文本/记忆产物**；任何状态写入都必须经由工具层（ToolRegistry）与服务层进入唯一写入者（Single Writer）`GameEngine`，提案经 Resolver 统一裁决（Resolution）后才可能被提交。三条红线（所有 Agent 必须遵守）：

1. 不持有领域对象引用，只能收到序列化后的感知切片（`PerceptionSlice`，Perception Slice；制造 Agent 为服务层投影的 `CraftView`，见 §8.2）；
2. 不直接调用仓储或 SQL，只能调用工具白名单（Tool Whitelist）中、`actor_scope` 内的工具（详见第 7 章）；
3. 所有数值、随机、掉落、伤害、制造计算在框架内完成，Agent 只负责理解意图、选工具、填参数、叙事包装。

六类 Agent 固定英文名与归属目录 `src/textgame/agents/`：

| Agent | 职责 | 输入（只读） | 输出 Schema | 模型分级 | 失败兜底 |
| --- | --- | --- | --- | --- | --- |
| `IntentParseAgent`（解析） | 把玩家自然语言解析为动作意图与工具调用，并给一句候选叙事 | 玩家原始输入 + 玩家私有感知切片 + 可见工具 JSON Schema | `ParseOutput`：`ActionIntent` + `tool` + `candidate_narrative` | 性价比模型 | 确定性关键词解析；仍失败则返回“无法处理”，不改状态 |
| `JudgeAgent`（裁判） | 仅处理 `resolution_policy=agent_assisted` 的规则空白场景，给倾向性裁决 | 该角色私有感知切片 + 规则空白说明 + Ruleset 摘要 | `JudgeOutput`：`verdict`/`reason`/`evidence_refs`/`confidence`，不产出数值 | 强模型 | 保守裁决（不产生有利结果）并标记“待作者确认” |
| `NarrativeAgent`（叙事） | 把已裁决事件包装成每屏 80～150 字的文本 | 已提交事件摘要 + 玩家可见切片 + 风格参数 + 候选叙事 | `NarrativeOutput`：`narrative`（长度受限）/`tone` | 性价比模型 | 模板渲染器按事件确定性生成文本 |
| `MemoryAgent`（记忆） | 生成记忆写入/遗忘指令与摘要 | 本角色私有记忆 + 本轮该角色可见事件 | `MemoryOutput`：`ops: list[MemoryOp]` + `summary` | 性价比模型 | 丢弃本次记忆更新（不阻塞回合） |
| `CharacterAgent`（角色） | 每个 NPC 一个实例，生产对话与行动提案 | 该 NPC 私有感知切片 + 该 NPC 私有记忆 + 可见工具 | `CharacterOutput`：`proposals`（≤2）+ `dialogue` + `memory_ops` | 性价比模型 | 本回合不行动（视为休眠），不产生事件 |
| `CraftAgent`（制造） | 自由制造的生成路径，产出制造方案 | 服务层投影的 `CraftView`（背包/工位/已知配方/玩家原话 ≤200 字，见 §8.2） | `CraftOutput`：`item_name`/`output_template_id`/`inputs`/`station`/`steps`（与第 13 章 `CraftDraft` 同构，见 §8.2） | 强模型 | 失败 → 拒绝并零写入（无匹配配方时无确定性回退；M5 接真实 LLM 后按第 13 章 §13.4 处理） |

注意：`JudgeAgent` 不是 `Resolver`。`JudgeAgent` 只产出带理由的**建议**，`Resolver` 是确定性代码，负责把建议变成可提交的 `Resolution`；默认判定策略仍是确定性，智能体覆盖必须携带显式理由（见第 10 章）。

**M5 出口附加项：裁判 Agent 已接线（2026-11-11，M5E-2，D-M5-14）**：契约落 `domain/judge.py`（`JudgeEvidence`/`JudgeOutput`、`verdict ∈ {allow, deny, modify}` + 只读 `allowed`、`JUDGE_CONFIDENCE_FLOOR=0.7`、证据上限 5；原「`agents/schemas.py`」不存在且破坏分层，故 DTO 放 domain、agent 层再导出）；`agents/judge_agent.py` 提供 `JudgeAgentLike`/`DeterministicJudgeAgent`/`LLMJudgeAgent`（`task="judge"`、`prompt_version="judge@v1"`、STRONG、`max_repair=1`；输入=脱内部 ID 的私有感知切片 + 提案 + 规则空白说明，证据必须落在切片内；失败/异常→`None` 交确定性兜底）；`needs_judge` 由 `ToolRegistry.agent_assisted_tools()` 派生（生产 8 工具全 `DETERMINISTIC` → 当前 0 消费者，机制就绪、测试注入可达）；`RuleEngine.verify_agent_override` 严格类型校验（非法一律「否」）+ `deterministic_fallback` 恒保守否决；**默认离线逐字等价、零模型调用**（旧 golden 与 demo/console `--check` 逐字不变）。cassette 5 个手工合成、零网络。

**M4 制造边界（D-M4-3 / D-M4-13）**：自由制造的**草案本身**不经裁决——`CraftAgent → CraftDraft → CraftService` 完成校验与数值重算后只产出草稿事件，`CraftProposal` 不进入 `ProposalQueue`（仅作 M5 契约保留），M5 接线真实 LLM 前必须迁移到 pre-queue（否则违反第 11 章 Resolver 纯函数约束）。这不等于「工具链路不接 Resolver」：M4 生产装配注入 M3 依赖后所有场景走 `_run_multi_actor`，玩家 `craft_item` 仍是 Proposal → `ProposalQueue` → 确定性 `Resolver`（无 Judge 覆盖）→ `ToolGate` → `CraftService` → `GameEngine`，失败提案照常写 `audit_events`（D-M4-13）。

### 8.2 私有感知切片与私有记忆：结构性防泄露

每个角色 Agent 的输入只含该角色的 `PerceptionSlice`（感知切片）与私有记忆，不接收 `GameState`、也不接收其他角色的记忆（`CraftAgent` 的输入是服务层由该玩家切片投影出的 `CraftView`，形式不同但可见信息不超出该切片，见本节末）。这不是 Prompt 里写“请不要泄露”，而是**构造上不可得**：切片由服务层方法生成并在组装阶段裁剪，Agent 只消费 `PerceptionSlice`，拿不到 `GameState`、仓储句柄或对象引用。

```python
class QueryService:   # services/query_service.py，第 6 章 6.3 定稿；Agent 只消费返回的切片
    def build_perception_slice(self, state: GameState, actor_id: str, *,
                               turn_id: int, save_seed: str,
                               plan_hint: str | None = None,
                               events: Sequence[Event] = ()) -> PerceptionSlice: ...
```

构造规则：

1. `visible_entities` 按可见性裁剪，NPC 只看得到同场景实体与公开状态；
2. `local_events` 只含该 actor 可见事件（`EventLog` 按可见性过滤，不给全局流水）；
3. `private_memory` 从 `MemoryStore` 按 `actor_id` 命名空间读取，跨角色不可见；
4. `plan_hint` 由调度器注入，不来自其他 Agent 的输出；
5. 切片交给 Agent 前已完成 JSON 序列化，禁止把 ORM 对象、引用或仓储句柄放进 Prompt。

Prompt 的组装顺序固定为：**系统约束 → 可用工具 JSON Schema → 感知切片 JSON → 私有记忆 → 玩家输入/触发原因 → 输出契约与示例**。输出模型用 Pydantic v2 定义，全部 `extra="forbid"`，多一个字段即视为违规：

```python
class ParseOutput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    intent: ActionIntent
    tool: ToolCall | None = None
    candidate_narrative: str | None = Field(default=None, max_length=200)
    clarify_question: str | None = Field(default=None, max_length=80)

class ToolCall(BaseModel):
    model_config = ConfigDict(extra="forbid")
    name: str = Field(pattern=r"^[a-z][a-z0-9]*(_[a-z0-9]+)*$", max_length=48)
    args: dict = Field(default_factory=dict)

class CharacterOutput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    proposals: list[Proposal] = Field(default_factory=list, max_length=2)
    dialogue: str | None = Field(default=None, max_length=150)
    memory_ops: list[MemoryOp] = Field(default_factory=list, max_length=3)

class JudgeOutput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    verdict: Literal["allow", "deny", "modify"]          # advisory only; no numbers
    reason: str = Field(min_length=1, max_length=300)
    evidence_refs: list[str] = Field(default_factory=list, max_length=5)  # refs within slice
    confidence: float = Field(ge=0.0, le=1.0)            # below 0.7 -> conservative fallback

class NarrativeOutput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    narrative: str = Field(min_length=80, max_length=150)  # 80-150 chars per screen
    tone: Literal["neutral", "tense", "warm", "grim"]

class MemoryOp(BaseModel):
    model_config = ConfigDict(extra="forbid")
    op: Literal["add", "update", "forget"]
    key: str = Field(min_length=1, max_length=64)
    text: str = Field(min_length=1, max_length=300)
    importance: int = Field(default=3, ge=1, le=5)
    ttl_turns: int | None = Field(default=None, ge=1)

class MemoryOutput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    ops: list[MemoryOp] = Field(default_factory=list, max_length=5)
    summary: str = Field(default="", max_length=300)

class MemoryStore(Protocol):
    """Per-actor private memory store; implemented in ch16 persistence/memory_store.py."""
    def load(self, actor_id: str) -> list[dict]: ...
    def apply(self, actor_id: str, ops: list[MemoryOp], *, turn_id: int) -> None: ...
```

以上类型为**回合内契约**（`agents/schemas.py`），统一由 `complete_json` 校验；`MemoryStore` 接口见本节，实现见第 16 章 `persistence/memory_store.py`（按 `actor_id` 隔离）。

**制造 Agent 的输入视图与输出映射（M4 口径，A-28/D-M4-1）**：`CraftAgent` 不直接消费 `PerceptionSlice`，而是服务层投影出的只读 `CraftView`（类型见第 13 章 §13.2 制造域契约）：背包清单、当前工位 `station_id`、已知配方 ID 列表 `known_recipe_ids` 与玩家原话 `free_description`（≤200 字，仅作数据）。M4 不接真实 LLM——生产默认关闭自由制造与模型调用，测试注入 `FakeLLM`；M4 也不修改 `PerceptionSlice`，M5 接线前回写第 5 章 `PerceptionSlice`（补 `inventory`/`known_recipe_ids` 等字段）后该投影退化为纯裁剪。`CraftOutput` 与第 13 章 `CraftDraft` **同构**（字段：`item_name`/`output_template_id`/`inputs`/`station`/`steps`），进入服务层直接按第 13 章 Schema 校验、无需字段改名：`inputs` 的 `template_id` 用 `ItemTemplateId`（`item.<name>`，不是实例 `item_<ULID>`，D-M4-1）；`station` 取房间 `ambient_tags` 的 `station.<name>`；产出模板必须出现在该配方 `item_templates` 中；**禁止 stats/damage 等任何数值字段**。产出物定义、数量等其余字段由 `CraftService` 按第 13 章契约补齐。

所有 Agent 输出统一经 `LLMClient.complete_json(LLMRequest)` 获取：返回 `Result`，成功时 `data={"parsed","usage","call"}`；Schema 校验失败进入一次修复重试，仍失败按上表兜底，**绝不把未校验输出写入状态**（详见第 12 章）。

**M5 出口接线已落地（2026-11-10，M5E-1，D-M5-13）**：`agents/llm_character_agent.py::LLMCharacterAgent`（`character@v1`）按本节契约实现——输入仅该角色 `PerceptionSlice`（含私有记忆），输出 ≤2 个 `Proposal`，经 `complete_json_with_repair` 一次修复，失败/离线/修复耗尽回退确定性 `CharacterAgent`（M3 计划表）；与 023 批量/休眠边界一致：消费私有切片 → 只能串行（不进批量），是否调用由编排层调度器决定（未唤醒零调用）。`agents/narrator_agent.py::LLMNarratorAgent`（`narrate@v1`）对应第 9 章叙事步（输入为已提交事件事实，不读玩家原文）；叙事/角色 Agent 均不写状态、不执行工具，只返回候选。

### 8.3 Prompt 结构与模型分级

| Agent | 模型档 | 模板槽位（`<agent_id>`，第 12 章管理） | 每回合调用上限 | 缓存策略 |
| --- | --- | --- | --- | --- |
| `IntentParseAgent` | 性价比 | `parse` | 1 | 相同输入哈希不缓存（随机性无关，但输入高熵） |
| `CharacterAgent` | 性价比 | `role` | 每个被唤醒 NPC 1 次 | 固定寒暄可缓存 |
| `NarrativeAgent` | 性价比 | `narrate` | 1 | 环境描述模板可缓存（`cachetools`/`diskcache` 见第 12 章） |
| `MemoryAgent` | 性价比 | `memory` | 每角色 1 次（可在响应后异步） | 不缓存 |
| `JudgeAgent` | 强模型 | `adjudicate` | 仅规则空白时 1 次 | 不缓存 |
| `CraftAgent` | 强模型 | `craft` | 仅自由制造时 1 次 | 相同材料组合+意图可缓存方案骨架 |

业务代码不得直接调用模型 SDK，统一走 `LLMClient.complete_json(LLMRequest)`（见第 12 章）；Prompt 采用 Jinja2 模板（`<agent_id>/<task>@v3.j2`），文件布局与版本由第 12 章统一管理，本章只约定模板槽位（系统约束/工具 Schema/感知切片/私有记忆/输入/输出契约）；`Event.params` 记录 `prompt_version`，便于回放（Replay）时定位“同状态不同输出”的原因。休眠策略：`CharacterAgent` 仅在被触发、进入同场景或计划触发点到达时调用，其余零成本。

### 8.4 编排层：LangGraph 还是自建 loop

**结论：主流程选 LangGraph（`pip 依赖`），多角色提案调度自建显式循环。** 即：一次玩家输入的“解析 → 判定 → 叙事 → 提交”回合流水线用 LangGraph `StateGraph` 编排；`ProposalQueue` 的收集、排序、裁决用普通 Python `while` 循环，不进图。

**2026-11-09 定案（M4 前，追认）**：M2/M3 实测后**主流程改为自建显式 loop**（第 17 章 D-M3-1 升级为正式决策）。主因：多角色提案是**动态长度循环**（玩家 1 + 被唤醒 NPC 0..N，drain ≤8）且提交必须走 CAS 单事务、冲突重试「只重裁决」；图只能包流程外壳，还得把事务与 LLM 调用留在图外，收益低于复杂度。LangGraph 仅保留第 16 章 `graph.py` 可选封装，留 M6 后或出现 HITL / 跨进程 durable execution 需求时评估（其触发条件见本节「何时改用另一种」）。

| 维度 | LangGraph | 自建 loop |
| --- | --- | --- |
| 回合内条件分支（降级/澄清/失败） | 条件边显式表达，拓扑可可视化 | 需要自己写状态机，分支易散落 |
| 状态持久化 | checkpointer 自带，但会形成第二份状态 | 只有 `EventLog`/`GameState` 一份权威 |
| 事务边界 | 节点内做 DB 事务不直观，易把 checkpoint 与业务事务混在一起 | 显式控制事务，最容易保证 CAS 提交 |
| 动态长度循环（多角色轮询） | 图要画成动态节点，可读性差 | 队列 + 循环天然适配 |
| 依赖重量 | 引入 `langgraph` + `langchain-core` | 零额外依赖 |
| 可观测性 | 图节点 trace 清晰 | 需自己埋日志 |
| 迁移成本 | M2 接入约 1.5 人日（`StateGraph` + `TypedDict` + 条件边） | 若后续退回，约 1 人日（保留 node 函数签名即可） |

取舍理由：

1. 回合内是**线性 + 少量条件分支**（校验失败、需要澄清、判定被拒、叙事失败），正好是 `StateGraph` 擅长的形状，且技术栈约束要求优先 LangGraph；
2. `ProposalQueue` 的元素数量随同场景角色数动态变化，且每个提案的裁决是纯函数，写成图反而增加复杂度；
3. **禁用 LangGraph checkpointer 作为状态权威**：`GameState` 与 `EventLog` 在 SQLAlchemy 中，回放以事件日志为准；checkpointer 至多用于 M5 的断点续跑（待定，见结论）；
4. 提交必须在单个数据库事务内完成 CAS（乐观并发控制，Optimistic Concurrency Control），放进图节点会模糊事务边界，因此 `GameEngine.submit` 保持图外的显式调用。

```python
class TurnState(TypedDict):
    turn_id: str
    player_input: str
    perception: dict
    parse: dict | None
    check: dict | None
    narrative: str | None
    result: dict | None

graph = StateGraph(TurnState)
graph.add_node("parse", parse_node)
graph.add_node("resolve", resolve_node)      # 确定性判定 + 可选 JudgeAgent
graph.add_node("narrate", narrate_node)
graph.add_node("commit", commit_node)        # 调 GameEngine.submit，图外事务
graph.add_conditional_edges("parse", route_after_parse,
    {"ok": "resolve", "clarify": END, "invalid": END})
graph.add_edge("resolve", "narrate")
graph.add_edge("narrate", "commit")
graph.add_edge("commit", END)

while pending := queue.drain(max_items=8):
    resolutions = resolver.resolve(pending, snapshot)   # 纯函数，不进图
```

何时改用另一种：若节点数稳定在 5 个以内、且 `langchain-core` 体积/冷启动成为部署硬约束，则回退为自建 loop（约 300 行，保留 node 函数签名）；反过来，若需要图内人工介入中断（HITL）、时间旅行调试或跨进程 durable execution，则把多角色调度也迁入 LangGraph，并同时把 checkpointer 只当缓存而非权威。

### 8.5 候选轮子

### 8.6 叙事 Agent 的流式渲染（N2-038/040，2026-11-12 落地）

- **只做显示层增量**：`LLMNarratorAgent.render_with_meta_stream` 在客户端实现可选
  `complete_json_stream` 时，把供应商原始 JSON 文本片段交给 `llm/streaming.py` 的
  `NarrativeDeltaExtractor`（纯函数 + 有状态薄封装：只认 `"narrative"` 字符串值；逐字符解
  `\"`/`\\`/`\n`/`\t`/`\uXXXX` 与 UTF-16 代理对；未完成转义跨 chunk 等待；提取上限 150+64），
  **只把已解转义的叙事前缀**交给 `on_delta`——原始 JSON 永不出模型层/前端。
- **校验与兜底不变**：完整 JSON 到达后仍走原 `NarrativeOutput` 校验 + 一次修复链；失败/两次不合格
  回退模板（已显示增量由接入层 `replace` 覆盖）。叙事仍只是候选文本，只有
  `done.result.text`/事件 `result.narrative` 落状态；`narrative_source = llm|template` 与事件
  `result.narrative_source` 一致（零事件只读回合为 `null`）。m3 多角色下 LLM 屏文本与 NPC 确定性
  短句拼接后若与已显示增量不同 → `replace`（`NARRATIVE_REVISED`）。
- **无流式客户端等价**：`RuntimeLLMClient` 内部客户端不支持流式时退回 `complete_json` 并**一次**下发
  （与缓存/幂等命中同口径）；接入层在「无已显示增量」时补一条完整 `delta`（不是 `replace`），
  前端无需感知差异。
- **证据（040 验收）**：离线生产装配 → `start → 单条 delta → done`、`done.result` 与 `/turns`
  等价（5 例验收测试见 `tests/integration/test_streaming_acceptance.py`）；真实 DeepSeek 探针首 delta
  **1.79–2.09s**、总 **2.53–2.99s**、`narrative_source=llm`、增量拼接 == 最终文本、
  `LLMCallRecord.streamed=true`；真实浏览器 e2e 29/29 步、157/157 断言。详见
  [ADR D-N2-1..N2-8](../decisions/2026-11-11-streaming-phase1.md) 与
  [040 进度文档](../progress/040-2026-11-12-streaming-acceptance.md)。

### 本章结论

1. 六类 Agent 的输出全部经 Pydantic v2 + JSON Schema 校验，`extra="forbid"`；未校验输出不进入 `ProposalQueue`，更不进入状态。
2. 私有感知切片与私有记忆在服务层组装时即裁剪，Agent 侧没有任何获取全局状态的 API——这是结构性的防泄露，不依赖模型自觉。
3. 模型分级按任务而非按角色：`JudgeAgent`/`CraftAgent` 用强模型，解析/叙事/记忆/角色用性价比模型；固定寒暄与环境描述优先命中缓存。
4. 编排结论：回合流水线用 LangGraph（`pip 依赖`，`langgraph>=1.2,<2`，入口 `langgraph.graph.StateGraph`），多角色提案调度用显式 `while` 循环；LangGraph checkpointer 不得作为状态权威。（2026-11-09 定案：主流程改为自建 loop，LangGraph 仅保留可选封装——见 §8.4 回写）
5. 执行建议：M2 先用 4 节点图打通单场景，同时写一套“同签名 node 函数”的自建 loop 作为降级开关；若 M3 前发现图节点无法覆盖动态多角色循环，则转为自建调度。（2026-11-09：M3 实测后已按本出口转为自建调度，并追认为正式决策）
