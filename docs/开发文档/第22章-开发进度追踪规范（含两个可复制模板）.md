### 22.1 双层追踪模型、vibe 切片与“一次开发会话”
- 单次进度文档（Progress Document）：`docs/progress/` 下一个可独立验证的切片（Slice）的记录，回答目标与验收、改动与提交、验证结果、下一步与风险（v0.3 轻量版）。
- 总体进展总览（Progress Overview）：`docs/PROGRESS.md`，只做汇总与索引；总览中每个数字必须能在单次文档找到证据（Evidence），否则视为无效更新。
- **vibe slice（切片）**：30–90 分钟可完成、可独立验证的垂直小功能；每天预计 4–8 个切片，trunk-based、小步提交、失败即回滚到上一绿点（VIBE-BRIEF §1）。**一次开发会话**（Development Session）= 一个切片（或若干相关切片的收尾），不是每次保存文件。里程碑（Milestone）与完成度（Completion Rate）的编号、计算规则见 22.3 与 22.5。

### 22.2 命名与序号规则
- 文件命名：`docs/progress/NNN-YYYY-MM-DD-<主题>.md`（与 `docs/progress/README.md` 一致）。
- `NNN`：三位数字，全局唯一、单调递增、永不复用；按 22.3 区间分配，跨区间不允许回填。
- `YYYY-MM-DD`：会话结束日，按 `Asia/Shanghai`（UTC+8）取本地日期，不因提交跨零点改日期。
- `<主题>`：ASCII kebab-case，2–5 个英文词，如 `turn-orchestrator-skeleton`；禁止空格、中文、大写（保证 grep 与 CI 稳定），中文说明写进正文；主题与第 17 章切片清单对应，一天可写多篇（每个切片一篇），编号连续递增。
- 提交信息 `progress: NNN <主题>`；单次文档与 `docs/PROGRESS.md` 必须在同一提交或同一 PR 内更新；作废文档不删除，正文首行标 `状态：作废（Superseded by NNN）`。
- 编号变更：超出预留篇数时向“下一个尚未开始区间”借号并登记总览第 4 节；示例 `001-2026-11-15-bootstrap-skeleton.md`。

### 22.6 更新时机与责任（vibe 节奏）

| 时点 | 动作 | 责任 | 强制程度 |
| --- | --- | --- | --- |
| 每个 vibe 切片结束（≤90 分钟，每日可多篇） | 新建单次文档 + 更新总览第 1、3 节 | 执行者（AI/人） | 强制（同一 PR） |
| 契约 / 事件 / 回放变更时 | 当次文档第 2 节契约对照 + 总览第 5 节偏离登记（仅此时填） | 人 | 强制（立即） |
| 切片失败或需要回滚 | 记录回滚点与原因；更新总览第 1、6、7 节 | 发现者 | 强制（当天） |
| 每日收尾（可选） | 汇总当日 NNN 到总览索引；活文档偏差写 1 行 | lead 或执行者 | 建议 |
| 里程碑结束 | 用 1 次会话回写计划偏差（不写长报告）+ 复审第 20 章风险 + 核对编号区间 | lead | 强制 |

建议的 CI 校验（M1 内实现、M5 前生效）：命名正则 `^\d{3}-\d{4}-\d{2}-\d{2}-[a-z0-9]+(-[a-z0-9]+)*\.md$`、编号唯一且落在区间、单次文档 ≤60 行、总览索引与目录一一对应、完成度可由任务清单复算、模板 4 节齐全——即 ADR 仓库所说的“决策即代码的适应度函数（Fitness Function）”。

### 22.7 与第 6、7 章 API 的对照要求（仅契约变更时填）
契约变更时，进度文档第 2 节末尾的对照表是唯一强制对照点（无契约变更写“无”即可）：
1. **服务层（第 6 章）**：每个新增/修改的写方法必须列签名、`ToolContext` 依赖的上下文字段、返回的 `Result`、`ErrorCode` 集合、产生的 Event 的 `method/params/result/rng_seed` 与幂等键来源；只写“新增了背包接口”视为不合格。
2. **工具层（第 7 章）**：每个新增/修改工具必须列 `ToolSpec` 六字段（name、description、json_schema、actor_scope、side_effect、resolution_policy），并给出可见性矩阵变化。
3. **偏离判定**：签名、字段名、错误码、事件结构、可见性或副作用标签与第 6、7 章任一处不一致即为**偏离**，必须写原因与方案（改代码 / 回改文档 / 新增 ADR）并由 lead 裁决，不允许静默偏离。
4. **状态变更**：GameState 字段、Event schema 版本、迁移脚本与固定种子回放结果须同时给出，回放不一致视为未完成。
5. **示例**：第 6 章定义 `craft_item(...) -> Result`，本次增加可选参数 `draft_id` → 记“兼容（扩展）+ 已回写第 6 章”；若把 `materials` 改为 `list[str]` → 记“破坏 + 需迁移”。

### 22.8 防流水账检查清单（vibe 短会话版）
- [ ] 切片目标与验收命令先写清；没有可执行验收命令的切片不算完成。
- [ ] 单次文档 ≤60 行、只写 4 节；只记改动/证据/下一步，不写过程叙事。
- [ ] 每个“完成”附证据（命令输出 / 测试数字 / 回放种子），无证据算未完成。
- [ ] 不贴大段 diff（>20 行给文件路径 + 提交号）。
- [ ] 契约变更才填偏离登记与 §22.7 对照；无变更写“无”。
- [ ] 完成度由任务计数算出，不写“大约 80%”。
- [ ] 失败切片必须写回滚点与原因，禁止连续堆叠未验证改动。
- [ ] 风险编号关联第 20 章（含 AI 编码风险）；下一步给“编号 + 主题 + 验收命令”。

### 本章结论
1. 进度追踪采用“单次进度文档 + `docs/PROGRESS.md`”双层结构，按 vibe 切片节奏更新：每个切片（30–90 分钟）结束写一篇并同步总览，两者必须在同一提交或 PR 内；计划是活文档，里程碑结束时用 1 次会话回写偏差。
2. 命名固定为 `NNN-YYYY-MM-DD-<主题>.md`，编号按第 17 章 M1–M6 区间预留（001–028），全局唯一、永不复用；一天可多篇，主题与切片清单对应。
3. 完成度仍只按“已通过测试的任务数 ÷ 里程碑总任务数”计算，任务清单以第 17 章 §17.2 切片明细为唯一来源；状态四选一（未开始/进行中/已完成/阻塞），阻塞优先。
4. 单次文档轻量化为 4 节（目标与验收命令 / 改动与提交 / 验证结果 / 下一步与风险），目标 ≤60 行/篇；接口偏离登记仅契约变更时填；CI 校验命名、编号区间、行数与 4 节齐全。
