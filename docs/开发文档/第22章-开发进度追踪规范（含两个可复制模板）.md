### 22.1 双层追踪模型与“一次开发会话”
- 单次进度文档（Progress Document）：`docs/progress/` 下一个可独立验证的功能切片（Feature Slice）的记录，回答目标、证据、偏差、接口变更、测试回放、风险与下一步。
- 总体进展总览（Progress Overview）：`docs/PROGRESS.md`，只做汇总与索引；总览中每个数字必须能在单次文档找到证据（Evidence），否则视为无效更新。
- **一次开发会话**（Development Session）：指一个可独立验证的功能切片（至少一条测试或回放可证明），不是每次保存文件；同一功能的反复调试合并为一次会话。里程碑（Milestone）与完成度（Completion Rate）的编号、计算规则见 22.3 与 22.5。

### 22.2 命名与序号规则
- 文件命名：`docs/progress/NNN-YYYY-MM-DD-<主题>.md`（与 `docs/progress/README.md` 一致）。
- `NNN`：三位数字，全局唯一、单调递增、永不复用；按 22.3 区间分配，跨区间不允许回填。
- `YYYY-MM-DD`：会话结束日，按 `Asia/Shanghai`（UTC+8）取本地日期，不因提交跨零点改日期。
- `<主题>`：ASCII kebab-case，2–5 个英文词，如 `turn-orchestrator-skeleton`；禁止空格、中文、大写（保证 grep 与 CI 稳定），中文说明写进正文。
- 提交信息 `progress: NNN <主题>`；单次文档与 `docs/PROGRESS.md` 必须在同一提交或同一 PR 内更新；作废文档不删除，正文首行标 `状态：作废（Superseded by NNN）`。
- 编号变更：超出预留篇数时向“下一个尚未开始区间”借号并登记总览第 4 节；示例 `001-2026-11-15-bootstrap-skeleton.md`。

### 22.6 更新时机与责任

| 时点 | 动作 | 责任 | 强制程度 |
| --- | --- | --- | --- |
| 一次开发会话结束、合并前 | 新建单次文档 + 更新总览第 1、3 节 | 开发者 | 强制（同一 PR） |
| 接口或工具签名变更时 | 当次文档第 3 节对照第 6、7 章，偏离登记总览第 5 节 | 开发者 | 强制（立即） |
| 里程碑状态变化或出现阻塞 | 更新总览第 1、6、7 节并关联风险编号 | lead 或发现者 | 强制（当天） |
| 里程碑结束 | 关闭开放问题、复审第 20 章风险、核对编号区间与第 4 节 | lead | 强制 |

建议的 CI 校验（M1 内实现，M5 前生效）：命名正则 `^\d{3}-\d{4}-\d{2}-\d{2}-[a-z0-9]+(-[a-z0-9]+)*\.md$`、编号唯一且落在区间、总览索引与目录一一对应、完成度可由任务清单复算、模板必填小节齐全——即 ADR 仓库所说的“决策即代码的适应度函数（Fitness Function）”。

### 22.7 与第 6、7 章 API 的对照要求
进度文档第 3 节是唯一强制对照点：
1. **服务层（第 6 章）**：每个新增/修改的写方法必须列签名、`ToolContext` 依赖的上下文字段、返回的 `Result`、`ErrorCode` 集合、产生的 Event 的 `method/params/result/rng_seed` 与幂等键来源；只写“新增了背包接口”视为不合格。
2. **工具层（第 7 章）**：每个新增/修改工具必须列 `ToolSpec` 六字段（name、description、json_schema、actor_scope、side_effect、resolution_policy），并给出可见性矩阵变化。
3. **偏离判定**：签名、字段名、错误码、事件结构、可见性或副作用标签与第 6、7 章任一处不一致即为**偏离**，必须写原因与方案（改代码 / 回改文档 / 新增 ADR）并由 lead 裁决，不允许静默偏离。
4. **状态变更**：GameState 字段、Event schema 版本、迁移脚本与固定种子回放结果须同时给出，回放不一致视为未完成。
5. **示例**：第 6 章定义 `craft_item(...) -> Result`，本次增加可选参数 `draft_id` → 记“兼容（扩展）+ 已回写第 6 章”；若把 `materials` 改为 `list[str]` → 记“破坏 + 需迁移”。

### 22.8 防流水账检查清单
- [ ] 每个“完成”都附证据（提交号 / 测试名 / 命令 / 回放种子），无证据算未完成。
- [ ] 不出现“优化了代码”“继续开发”“基本可用”等无判据表述。
- [ ] 不粘贴大段代码 diff（超过 20 行给文件路径与提交号代替）。
- [ ] 完成度由任务计数算出，不写“大约 80%”；偏差必写原因与处理。
- [ ] 接口变更必须对照第 6、7 章，有偏离就登记。
- [ ] 测试结果给命令与 passed/failed/skipped 数字；回放给种子。
- [ ] 风险必须编号并关联第 20 章，不写“注意风险”。
- [ ] 下一步必须是“编号 + 主题 + 前置依赖”；模板小节不得删改，空项写“无”；单次文档正文 ≤ 150 行、总览 ≤ 80 行。

### 本章结论
1. 进度追踪采用“单次进度文档 + `docs/PROGRESS.md`”双层结构：单次文档给证据、总览给索引，两者必须在同一提交或 PR 内更新。
2. 命名固定为 `NNN-YYYY-MM-DD-<主题>.md`，编号按第 17 章的 M1–M5 区间预留（001–004、005–009、010–014、015–018、019–024），全局唯一、永不复用。
3. 完成度只按“已通过测试的任务数 ÷ 里程碑总任务数”计算，任务清单以第 17 章为唯一来源；状态四选一（未开始/进行中/已完成/阻塞），阻塞优先。
4. 进度文档第 3 节必须与第 6、7 章 API 对照（签名、`Result`/`ErrorCode`、Event、`ToolSpec` 六字段与可见性），任一处不一致即标“偏离”并由 lead 裁决；防流水账靠“无证据不算完成、完成度可复算、模板不删改”三条硬规则，CI 校验须在 M5 前生效。
