### 9.1 调用链总览与调用预算

一个回合（Turn）指一次玩家输入到状态提交的全过程。**调用预算以第 12 章 12.8 为准**：单回合默认 2 次、最多 3 次 LLM 调用（超出走确定性兜底），首版端到端 P95 ≤8 s、M2 缓存命中目标 ≤3 s；本章只讲调用链，不另立预算数值。快照（Snapshot）指 `GameState` 的持久化投影，回放以 `EventLog` 为准。默认 2 次为**解析（合并候选叙事）1 次 + 可选叙事润色 1 次**；判定结果与候选叙事不冲突时跳过润色。强模型裁判只在“规则空白且需要裁决”时出现；记忆摘要放到响应之后异步执行，不占关键路径。

回合编排的输入/输出 DTO（`TurnOrchestrator.run` 契约，第 21 章 §21.2.6 使用）：

```python
class TurnInput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    player_id: str = Field(min_length=1)
    text: str = Field(min_length=1, max_length=500)
    idempotency_key: str = Field(min_length=1)
    save_seed: str = Field(min_length=1)      # 存档级种子，供第 10 章派生随机

class TurnResult(BaseModel):
    ok: bool
    turn_id: int | None = None
    text: str = ""
    events: list[Event] = Field(default_factory=list)   # 提交成功后的盖章态事件
    error_code: ErrorCode | None = None
    # 构造器：clarify() / from_resolution() / failed()，见第 21 章 §21.2.6
```

```text
客户端 POST /api/v1/turns
  → 接入层（FastAPI）鉴权 + 幂等键
  → TurnOrchestrator（turn_id、全局 seq、快照版本）
  → QueryService.build_perception_slice（私有感知切片 + 工具白名单）
  → IntentParseAgent（LLM #1：ActionIntent + tool + 候选叙事）
  → ToolRegistry 门（白名单/actor_scope/JSON Schema）
  → RuleEngine + Resolver（确定性）；必要时 JudgeAgent（LLM #可选）
  → CharacterAgent 提案（被触发的 NPC，各自私有切片）
  → ProposalQueue → Resolver.resolve
  → NarrativeAgent（LLM #2：仅当候选叙事不可用）
  → GameEngine.submit（CAS 事务，唯一写入者）
  → EventLog + Response（80～150 字）
```

### 9.2 编号步骤与失败分支

1. **接入与幂等**：客户端带幂等键（`Idempotency-Key`，Idempotency Key）。接入层校验后创建 `turn_id`，同一幂等键的重复请求直接返回上次结果（详见第 6、12 章）。失败分支：鉴权失败 → HTTP 401；重复键但参数哈希不同 → `CONFLICT`。
2. **载入快照并生成感知切片**：`TurnOrchestrator` 读取当前 `GameState` 快照与版本号，调用 `QueryService.build_perception_slice(actor_id, turn_id, save_seed)`（第 6 章 6.3 定稿），再按 `actor_scope` 过滤工具 Schema。失败分支：快照不存在/损坏 → `INTERNAL`，不进入模型调用。
3. **LLM 调用 #1（合并）**：`IntentParseAgent` 通过 `LLMClient.complete_json(LLMRequest)` 一次返回 `ActionIntent`、`tool` 与 `candidate_narrative`（对应“能一次调用完成的不要拆两次”；返回结构见第 12 章，不在本章展开完整签名）。失败分支：超时/限流 → `complete_json` 内部指数退避重试；仍失败返回 `LLM_UNAVAILABLE` → 确定性关键词解析（映射常见动词到工具）；解析仍失败 → 返回“无法理解，请换个说法”，零状态变更。
4. **Schema 校验与修复重试**：模型原始文本不符合输出 Schema → `SCHEMA_VIOLATION`，由 `complete_json` 把错误回传模型修复一次；仍失败按上一步兜底，该结果不进 Resolver、不写状态。
5. **工具门校验**：`ToolRegistry` 检查工具存在、`actor_scope` 允许、参数符合工具的 JSON Schema、副作用标签（Side-effect Tag）合法。失败分支：工具不在白名单或不在 `actor_scope` → `NOT_ALLOWED`；工具参数不符合 JSON Schema → `INVALID_INPUT`；两者都返回提示或转澄清；若解析置信度低（`confidence < 0.6`）→ 改为澄清提问，零状态变更。
6. **确定性判定**：`RuleEngine` 计算命中/伤害/发现等结果，随机数来自 `RandomSource`；规则空白时按 `resolution_policy` 决定是否调 `JudgeAgent`（强模型）。失败分支：裁判超时/低置信度 → 保守裁决，并在 `Resolution.reason` 中记录“降级为确定性保守判定”。裁判证据（`JudgeOutput`）随提案在步骤 9 作为 `judgements` 传入 `Resolver.resolve`。
7. **组装玩家提案**：`Proposal(turn_id, actor_id, tool, args, reason, priority)`；玩家动作默认 `priority=100`。
8. **唤醒角色 Agent**：只唤醒“被触发/同场景/计划触发点”的 NPC（休眠策略），各自用私有切片并发调用；默认每个 NPC 单独调用（信息隔离），合并条件见 9.3。失败分支：单个 NPC 失败不影响其余，按“不行动”处理并计入审计。
9. **裁决**：`ProposalQueue` 按 `(priority desc, 入队序号 asc)` 排序（入队序号是队列内部计数器，不是 `Event.seq`），`Resolver.resolve(proposals, snapshot, judgements)` 逐条校验前置条件与冲突（裁判证据由步骤 6 传入，可为空），输出 `Resolution` 列表（verdict 取值：`applied`/`rejected`/`conflict`/`deferred`）。
10. **叙事**：候选叙事与最终事件一致时直接复用（0 次调用）；不一致或事件含关键数值/失败语义时调 `NarrativeAgent` 润色（LLM #2），强制 80～150 字。**叙事候选与润色结果都在提交前生成，只有提交成功后才返回**；提交失败则丢弃候选与润色结果、只返回错误。失败分支：超时 → 模板渲染器根据事件生成确定性文本。
11. **原子提交**：`GameEngine.submit(expected_version, events, idempotency_key)` 单事务内校验版本、写事件、更新快照；版本冲突时重新载入快照并**只重跑裁决**（不重调模型），最多 3 次尝试（首次 + 2 次重试，第 11 章展开）。
12. **响应与异步副作用**：返回叙事、可见效果、建议动作与用量（`llm_calls`/`tokens`/`latency_ms`）；回合提交后异步触发 `MemoryAgent` 摘要，不阻塞响应。

| 失败点 | 处理 | 错误码/结果 |
| --- | --- | --- |
| 模型超时/不可用 | 退避重试 → 关键词解析 → 无法处理 | `LLM_UNAVAILABLE` / 正常提示 |
| LLM 原始输出不合规 | 一次修复重试 → 兜底 | `SCHEMA_VIOLATION`（内部审计） |
| 工具越权（白名单/`actor_scope`） | 拒绝，转澄清 | `NOT_ALLOWED` |
| 工具参数不符合 JSON Schema | 拒绝，转澄清 | `INVALID_INPUT` |
| 判定被拒 | 不生成状态事件，叙事说明原因 | `Resolution.verdict=rejected` |
| 提交版本冲突 | 重载→重裁决→重提交，最多 3 次尝试（首次 + 2 次重试） | `CONFLICT` |
| 叙事失败 | 模板渲染 | 降级文本 |

### 9.3 串行 vs 合并调用

取舍原则是“**同信息边界才可合并**”。合并调用会把多个角色的上下文塞进同一个 Prompt，若这些角色私有记忆不同，就破坏了第 8 章的结构性防泄露，因此：

- **允许合并**：解析 + 候选叙事（同一玩家、同一切片）；同一公开场景内、无私有记忆差异的 NPC 对话（例如广场上两名卫兵的广播式回应），且每批 NPC ≤ 4；
- **默认串行并发**：不同 NPC 各自持有私有记忆时，用 `asyncio.gather` 并发调用（各自独立 Prompt），以并发换延迟，但绝不在一个 Prompt 中混合私有信息；
- **一次调用完成合并清单**：(a) 同一信息边界；(b) 同一模型档；(c) 输出可逐项校验；(d) 单项失败可独立兜底；(e) 合并省下的延迟/成本大于 Schema 失败的影响面。
- **多 NPC 批量输出格式**：`{"agents": [{"actor_id": "...", "dialogue": "...", "proposals": [...]}]}`，逐项按 `actor_id` 与工具白名单校验；任一项失败只丢弃该项。

结论：默认 2 次调用（解析合并候选叙事 + 必要时叙事润色），多 NPC 场景用并发独立调用；批量合并只作为“公共场景 + 预算受限”的优化开关，不作为默认。

### 9.4 示例 JSON 流

玩家输入：`我举起火把照向洞穴深处，想看看有没有脚印。`

LLM #1 输出（解析 + 候选叙事，已过 Schema 校验）：

```json
{
  "intent": {"action": "inspect", "target": "cave_entrance",
             "params": {"light": "torch", "focus": "footprints"}, "confidence": 0.86},
  "tool": {"name": "inspect_scene", "args": {"focus": "footprints", "light": "torch"}},
  "candidate_narrative": "火把的光在湿漉漉的岩壁上摇晃，你蹲下身，在泥地上找到几枚模糊的脚印。"
}
```

确定性判定结果（`RuleEngine` 计算，随机来自 `RandomSource`；示例种子由 `RandomSource.derive_seed(save_seed="demo-save-2026", turn_id=42, actor_id="player_1", method="inspect_scene", seq=41)` 派生并掩码到 63 位）：

```json
{
  "rule_id": "perception.track_v1",
  "actor_id": "player_1",
  "target": "cave_entrance",
  "dc": 12,
  "dice": [{"sides": 20, "rolls": [15], "kept": [15]}],
  "modifiers": [{"source": "perception", "value": 3}],
  "total": 18,
  "outcome": "success",
  "rng_seed": 7917514595543340859
}
```

提案与裁决：

```json
[
  {"proposal": {"turn_id": 42, "actor_id": "player_1", "tool": "inspect_scene",
                "args": {"focus": "footprints", "light": "torch"},
                "reason": "玩家明确要求观察脚印", "priority": 100},
   "resolution": {"proposal_id": "p_000042_001", "verdict": "applied",
                  "reason": "目标可见，判定成功",
                  "applied_events": [
                    {"turn_id": 42, "actor_id": "player_1", "method": "inspect_scene",
                     "params": {"focus": "footprints", "light": "torch",
                                "proposal_id": "p_000042_001"},
                     "result": {"ok": true,
                                "data": {"clue_id": "footprint_a", "direction": "north"}}}
                  ]}}
]
```

`Resolution.applied_events` 是**草稿态 `Event` 对象**（无 `id`/`seq`/`ts`/`rng_seed`）：`Resolver` 只产出待提交事件，盖章由 `GameEngine.submit` 在事务内完成（与第 5 章“草稿态/盖章态”校验、第 11 章、第 21 章 §21.2.2 伪代码一致）。

提交后的事件（基线字段）：

```json
{
  "id": "evt_000041",
  "turn_id": 42,
  "seq": 41,
  "actor_id": "player_1",
  "method": "inspect_scene",
  "params": {"focus": "footprints", "light": "torch", "proposal_id": "p_000042_001"},
  "result": {"ok": true, "data": {"clue_id": "footprint_a", "direction": "north"}},
  "rng_seed": 7917514595543340859,
  "ts": "2026-11-08T12:00:03Z"
}
```

事件序号为**全局口径**：`Event.seq` 是每个存档从 1 起、跨回合连续单调递增的全局事件序号，`Event.id = f"evt_{seq:06d}"`，同回合事件按 `seq` 升序排序（与第 5、14 章一致）。

响应（`TurnResponse` 为接入层 DTO，字段可随第 6 章细化）：

```json
{
  "turn_id": 42,
  "ok": true,
  "narrative": "火把的光在湿漉漉的岩壁上摇晃。你蹲下身，泥地上有几枚模糊的脚印，脚尖都朝着洞穴深处。",
  "effects": [{"type": "clue_discovered", "clue_id": "footprint_a"}],
  "suggested_actions": ["follow_tracks", "listen", "leave"],
  "usage": {"llm_calls": 1, "prompt_tokens": 612, "completion_tokens": 168, "latency_ms": 1840}
}
```

### 本章结论

1. 单回合固定 12 个步骤，LLM 调用默认 2 次、最多 3 次（预算 SLO 以第 12 章 12.8 为准）；解析与候选叙事必须在一次调用内完成，判定通过后只在需要时润色。
2. 多角色调用默认“各自私有 Prompt 并发”，只有同公开感知、无私有记忆差异且 ≤4 个 NPC 时才允许批量合并，以防结构性泄露。
3. 每个失败点都有确定性兜底（Deterministic Fallback）：解析→关键词、裁判→保守裁决、叙事→模板、提交→最多 3 次尝试后 `CONFLICT`；任何兜底都不写未校验数据。
4. 执行建议：M2 验收标准为“默认 2 次、最多 3 次 LLM 调用、失败回合零状态变更”；延迟/成本 SLO 引用第 12 章 12.8（首版 P95 ≤8 s、M2 缓存命中目标 ≤3 s），不另立数值。
5. 待定项：记忆摘要在 M2 采用“响应后异步、失败丢弃”，M3 再评估是否合并进 LLM #2（方案 A 异步独立调用；方案 B 与叙事合并一次调用换取成本，但违反信息边界；方案 C 用确定性摘要器，不调模型）。
